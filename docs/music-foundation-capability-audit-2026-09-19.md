# 音乐基础能力审计与修复路线（2026-09-19）

## 结论

当前项目已经具备可靠的微内核编辑机制，也能完成单谱表、单声部、单音的基础记谱闭环；但“音乐基础层”还没有完整达到商业软件可用标准。这里必须严格区分“微内核完成度”和“第一方音乐插件／产品完成度”，两者不是一张待办表。

主要问题不是内核缺少具体音乐功能，而是通用机制、第一方音乐插件和产品投影之间存在断层：部分能力只在 Core 最小结构模型中存在，工作台显示、输入、播放、复制粘贴尚未接通；延音线、速度时间线、谱号变化、吉他定弦等具体音乐语义应由第一方插件定义并持久化，不能继续扩大内核 schema。

本文件把本轮审计和此前调性／移调审计的结果共同登记为后续修复清单，但按“微内核机制／插件宿主机制／第一方音乐插件／产品闭环”四条工作流分别归责。后续实现不得只完成界面或只增加 DTO；每项基础能力必须至少覆盖保存、加载、编辑、撤销、重做、重放、投影和结构化错误处理。

明确边界：Tie、Slur、力度、演奏法、连音组分组、反复结构、调号、速度变化、谱号变化、吉他定弦与技巧都不是微内核功能。内核只提供让这些插件安全实现所需的身份、引用、事务、权限、历史、资源限制和错误机制。

## 审计范围与判断方法

本轮核对了以下层次：

- TypeScript Core 与 Rust `brilliant-score-foundation` 的权威乐谱模型；
- Core 公共命令、批事务、范围操作、扩展所有权与跨模块读取；
- 工作台输入合同、Notation Projection、刻谱和播放 Projection；
- 范围选择、复制粘贴、原生项目保存与现有导出；
- 调号第一方模块和既有派生发声音高边界设计。

“模型中有字段”不等于功能已经完成。本审计按以下完整链路判断：

```text
持久化事实 → 公共命令 → 原子事务/历史 → Projection → 编辑与显示
                                      └→ 播放/导出
```

任一关键环节缺失，都记为“部分实现”或“未实现”。

## 两本账：内核不足与第一方插件缺口

### A. 微内核／Module SDK 机制结论

| 机制 | 当前状态 | 为什么属于内核 |
| --- | --- | --- |
| Extension 对 Core 实体的引用／触发声明 | payload 可以保存 ID，但没有供插件平台查询的机器可读声明 | 属于 Module SDK／Registry 与插件平台的共享合同；不要求 Store 理解插件 payload |
| Reconciliation 自动组合 | 内核已经能把 Core 编辑与显式 reconcile 命令放进同一 Batch，并在最终校验失败时整批回滚；目前需要调用方显式组装 | 属于插件平台调度；内核继续负责权限、原子提交、历史与最终校验，不应暗中执行音乐规则 |
| 插件可请求的 Core Effect 合同一致性 | 本轮已把 TS Module SDK V1 补齐到 Native 已支持的六类请求，并统一复用 Core 命令解码／准备；定向与完整回归通过 | 已关闭 |
| Note 子实体编辑 | V1 可在同一 Batch 中删除原 Event，再按原锚点插入修改后的 Notes Event；插件现在也可请求这两类 Effect | 功能已具备；独立 Note insert/remove/move 命令仅是未来 V2 的效率／易用性优化，不能为此破坏冻结的 28 命令 V1 |
| 声明读取的精确依赖闭包 | 已有显式跨插件读取；文档仍明确未证明精确依赖闭包和增量等价 | 商业规模下需要正确判断哪些插件必须重跑，不能靠全量扫描长期兜底 |
| 多插件聚合资源与性能资格 | 单插件预算、Wasm 边界等已有大量保护；跨插件聚合限制和正式性能资格仍在剩余工作中 | 属于内核运行时的可预测性和抗失控能力 |

引用／触发声明与自动组合应由 Module SDK、Registry 和应用级插件平台共同完成，不能把隐藏的自动回调塞进 Store。当前没有必须新增的音乐专用 Core 命令；精确依赖闭包和聚合资格属于商业硬化，不要求内核认识任何音乐概念。

当前**不需要**把 Extension owner 扩大到 Measure／Event／Note。Score／Part-owned 稀疏块配合显式 Core 引用已经足以承载第一版；盲目增加 owner 类型会扩大存储、迁移和权限复杂度。

### B. 第一方音乐插件待实现

| 第一方插件 | 拥有的具体语义 | 依赖的通用机制 |
| --- | --- | --- |
| Key Signature | 稀疏调号变化、继承和合法范围 | 基础 V1 已完成；继续依赖引用生命周期 |
| Tie | 音符端点、同音规则、链、显示与播放合并 | Core 引用声明与 reconciliation |
| Pitch Transformation | 业务级移调、调号联动、拼写策略、等音重拼写 | 原子多 Effect、书写音高 Effect |
| Tuplet Group | 连音组成员、比例显示、括号和编号 | Event 引用、时值 Effect、reconciliation |
| Tempo Timeline | 稀疏速度变化、渐变速度语义 | Measure／时间位置引用、Projection 贡献 |
| Clef Timeline | 稀疏谱号变化与继承 | Staff／Measure 引用、Projection 贡献 |
| Dynamics／Articulation | 力度、渐强渐弱、重音、断音等 | 位置／范围引用、播放 Projection |
| Repeat Route | 反复、房子和有界播放路线 | Measure 引用、结构校验、播放 Projection |
| Guitar Foundation | 定弦、变调夹、弦品、多把位和可演奏性 | Note／Part 引用和稳定 Projection |

这些插件负责自己的 schema、命令、校验、修复策略和投影。即使由项目官方开发，也必须走与第三方插件相同的权限和事务合同。

### C. 插件宿主／工作台缺口，不计入内核

- 可组合 Notation／Playback Projection；
- 和弦、多 Voice、弱起和完整时值的输入与显示；
- 单个 MIDI 越界音的局部播放降级；
- 带插件片段的复制粘贴和 ID 映射协调；
- Concert Pitch 视图切换；
- MusicXML／MIDI／Guitar Pro 适配器装配；
- UI 入口、设置、警告开关和用户反馈。

应用级插件平台并非从零开始：`docs/plugin-platform-plan-v1.md` 记录的平台 facade、稳定前端 SDK、启停、设置隔离、Manifest 预检和第一方 UI 插件迁移已经完成。后续仍需桌面受控发现、签名／来源、升级迁移与回滚，以及本文件要求的音乐关系触发、Projection 和 fragment 组合。它们应在插件平台会话继续建设，不进入微内核 Store，也不在本轮重复实现。

这三类待办今后必须分别统计。第一方插件或工作台没完成，不能再表述成“微内核缺少延音线／力度／吉他技巧”。

## 已经可靠具备的基础

### 微内核机制

现有内核已经提供：

- 稳定实体 ID 与文档、Part、Staff、Measure、Voice、Event、Note 层级；
- 严格编解码、引用校验、资源预算和结构化失败；
- 原子 Batch、撤销、重做、历史重放与候选态验证；
- Part／Staff／Voice／Measure／Event 的插入、删除、移动和字段修改；
- 范围删除和范围书写音高移调；
- 扩展块、贡献执行、跨插件显式读取、降级只读与错误归因；
- 可容忍的超拍规则告警，不会因轻度谱面问题阻止保存和继续编辑。

这些能力足以继续承载音乐模块，后续不应把具体音乐技巧重新塞回微内核。

### 当前音乐事实

Core 已经能够保存：

- `WrittenPitch { step, alter, octave }`，保留同音异名；
- `writtenToSounding` 移调关系；
- 1 到 64 分音符、0 到 3 个附点和 `timeModification` 比例；
- 每小节拍号、弱起长度；
- 多 Part、多 Staff、多 Voice；
- 一个事件中的多个音符，即和弦事实；
- Voice 起点和事件跨谱表分配；
- 稀疏 Part 级标准调号变化（第一方模块）；
- 标题、作者和一个全局 BPM。

### 当前产品闭环

工作台目前稳定接通的是：

- 单 Part、单五线谱、单 Voice；
- 单音与休止符输入；
- 常用时值、单附点、基础升降号；
- 拍号编辑、初始谱号编辑、全局 BPM；
- 稀疏调号设置、替换、继承、渲染和撤销重做；
- 普通自动连桁；
- 选区删除和简单事件复制粘贴；
- 原生项目保存／打开、五线谱 SVG 导出和基础播放。

普通自动连桁已经通过刻谱引擎按拍号派生，不应再列为缺失功能。缺失的是用户指定的断桁、跨拍连桁和不规则拍号的明确分组。

## 关键机制缺口及归属

### 1. 插件宿主：Projection 仍然以硬编码白名单处理扩展

Notation 和 Playback Projection 当前只认识调号扩展。文档中一旦出现其他扩展块，整份乐谱就可能返回 `unsupported`。

如果继续保持这种做法，新增延音线、力度、歌词或吉他指法模块后，插件越多，基础显示和播放反而越容易失效。这与微内核加模块的目标冲突。

需要改为可组合 Projection：

- 基础 Projection 始终投影它能理解的 Core 事实；
- 已注册模块通过受限贡献补充其视图数据；
- 无关的未知扩展保持无损但不阻止基础显示；
- 必需模块缺失或 schema 不兼容时，按现有降级合同进入明确的只读／能力不可用状态；
- 单个模块的显示或播放能力不足，不能伪装成整份文档损坏。

这是继续增加音乐模块前的 P0 宿主／插件平台修复。微内核只需提供稳定只读快照、受限贡献调用和故障归因，不负责 Notation 或 Playback 的具体组合逻辑。

### 2. 微内核：扩展中的实体引用没有通用生命周期协议

扩展块目前直接归属 Score 或 Part。模块可以在 payload 中引用 Measure、Voice、Event、Note ID，但内核不会自动理解这些引用。

现有跨插件读取解决了“谁能读谁”，没有解决：

- 删除 Core 实体时哪些模块关系必须删除、截断或迁移；
- 批量移动、复制和粘贴时如何重映射引用；
- 多模块清理如何与 Core 删除进入同一原子事务；
- 撤销、重做、重放后如何恢复完全一致的关系图。

调号删除小节目前可以由宿主专门组合“删除变化点 + 删除小节”，已有关系消费者测试也证明“Core 编辑 + reconcile 命令”能够共享一个 Batch、一个历史项并在部分修复时整批拒绝。缺口在于调用方仍需知道每个插件的专用命令，这种特例无法扩展到延音线、力度、歌词、指法等几十种模块。

正确的通用机制应保持显式分层：

1. 模块通过 SDK 声明其 extension payload 对 Core 实体的引用和受影响触发类型；
2. Registry 对声明做身份、版本、权限和依赖校验；
3. 插件平台在应用命令边界确定相关模块，按已验证依赖顺序显式组装 Core 命令与 reconcile 命令；
4. 内核按现有 Batch／Effect 合同执行，模块只能返回其有权修改的效果；
5. 所有清理与原 Core 命令一次提交、一次撤销，任何不完整修复由最终校验整批拒绝；
6. 未安装模块和未来 schema 继续按无损只读规则处理；资源预算、错误归因和确定性顺序沿用现有合同。

内核负责声明的可信边界、原子执行和最终一致性；插件平台负责触发与排序；具体“删除音符后如何处理延音线或歌词”由对应插件决定。内核不识别 Tie、歌词或其他音乐概念，也不在普通 Core 命令后偷偷追加业务操作。

### 3. 插件宿主：复制粘贴合同只能保存简单事件

当前剪贴板只保存简化的 `EventProperties[]`，范围还限于同一小节和 Voice。它不能携带：

- 和弦中的多个 Note；
- 延音线和其他跨事件关系；
- 力度、演奏法、歌词、吉他把位；
- 调号、谱号、速度等范围内变化；
- 稳定 ID 的关系重映射信息。

需要模块参与的 fragment export/import 协议。每个模块导出与选区相关的片段，宿主协调新 ID 分配和引用映射，再通过内核 Batch 原子提交。协议完成前，关系型内容的复制必须返回明确限制，不能静默丢失语义。片段格式和产品选择范围属于宿主／插件平台；内核只负责原子提交、权限与引用一致性。

## P0：商业音乐基础层必须补齐（不是微内核功能清单）

以下条目描述第一方音乐插件和工作台的产品能力，用于衡量整个音乐平台是否商业可用。除条目中明确指出的通用 CRUD／引用机制外，不得据此把具体音乐语义写入微内核。

### P0-1 延音线 Tie

当前没有跨事件、跨小节连接同一发声音高的事实模型。延音线不是纯视觉装饰，它改变音符持续时间和播放 Note On／Note Off 行为。

由必装的 Tie 第一方插件保存稀疏关系：源 Note ID、目标 Note ID 和必要的方向／链信息。内核只提供引用生命周期和原子事务，不理解“同音才允许连接”、延音链或播放合并等音乐规则。

最低验收：

- 同音相邻事件和跨小节事件可以建立、删除延音线；
- 删除、移调、复制或替换任一端点时得到确定的修复或明确拒绝；
- 延音链显示连续，播放只触发一次发声并延长时值；
- 保存重开、撤销重做、历史重放结果一致；
- Tie 与 Slur 分开，不能用一个视觉曲线字段混用。

### P0-2 和弦端到端

Core 可以在同一事件保存多个 Note，但工作台输入、Notation Projection 和 Playback Projection都要求恰好一个音符。

Core 公共命令还能创建一个多音符事件、修改已有 Note 的音高，但缺少对子实体 Note 的通用插入、删除和重排 CRUD。内核只需要补足这组通用结构操作；“和弦输入、和弦名称、音程规则和刻谱交互”由第一方记谱／编辑插件实现。用“删除整个事件再新建”代替会改变 Event ID，并破坏外部关系。

最低验收：

- 在现有事件中原子增加／删除单个 Note；
- 禁止把 notes 事件删成空集合，或明确原子转换为休止符；
- 和弦输入、选择、单音编辑、刻谱和同时播放闭环；
- 每个 chord tone 保留独立 Note ID，延音线和指法可以稳定引用；
- 复制粘贴和范围移调保留整个和弦。

### P0-3 多声部端到端

Core 和公共命令已经支持多 Voice，工作台显示与播放仍要求每小节只有一个 Voice。吉他谱中旋律与低音使用独立时值是常见基础需求。

最低验收：

- 增删 Voice、选择 Voice、在指定 Voice 输入；
- 同一小节多 Voice 对齐显示，符干、休止符和碰撞处理可读；
- 播放按 Voice 起点并行调度；
- 范围选择、删除、复制粘贴明确限定或跨越 Voice；
- 超拍／欠拍告警按 Voice 定位，不能把一个 Voice 的状态误算到另一个。

### P0-4 节奏闭环

Core 的时值模型比工作台更完整，但仍没有形成产品闭环：

- 工作台仅输入 1／2／4／8／16 分音符，32 分休止符只用于补空隙；
- 只支持 0 或 1 个附点；
- Notation 和 Playback Projection 拒绝 `timeModification`；
- Notation 和 Playback Projection 拒绝弱起；
- 一个事件出现三连音会使整份视图或播放不可用。

还需区分“内核已有的数学时值比例”和“Tuplet 第一方插件拥有的记谱关系”。单个事件上的 `timeModification` 可以计算时长；多个事件属于同一连音组、编号／括号范围以及嵌套关系，应由插件表达。

最低验收：

- 1–64 分音符、0–3 附点能够输入、编辑、显示和播放；
- 弱起从文档到显示、导航、播放完整接通；
- 常用 N:M 连音组有稳定组 ID、范围和显示语义；
- 不支持的极端嵌套只限制目标内容，不让整份乐谱失效；
- 精确分数贯穿编辑和播放，不退化成浮点节拍累积。

### P0-5 Pitch Transformation V1 第一方插件

此前调性审计发现的内容全部保留为必修项：

- 增加上层音乐命令，例如 `brilliant.notation.pitch-transform.apply`；
- 一个业务操作原子组合音符移调与调号变化；
- 增加保留字母、优先升号、优先降号、调号感知、最少临时变音等拼写策略；
- 增加真实工作台入口；
- 增加等音重拼写；
- 修改移调乐器时支持“保持书写音高”和“保持实际发声”两种明确语义；
- 后续 Concert Pitch Projection 使用同一事实源，不能保存第二份音符或调号。

同时要消除基础输入与 Core 能力的不一致：Core 可以保存八度 0–8 和双升／双降，工作台目前只接受 C2–B6 以及单升、单降、还原。产品可以按乐器缩小默认可视音域，但不能把合法 Core 音高变成整谱 `unsupported`；超出当前控件范围的音符至少必须可显示、选择和精确编辑。

底层 `core.range.transpose-written-pitch` 继续作为明确音程变换机制，不承担调号决策和自动拼写策略。业务级转调、调号联动和拼写策略全部属于第一方插件。

### P0-6 播放宿主的 MIDI 越界行为与既定合同不一致

设计文档已经规定：派生 MIDI 不在 0–127 时，该音的 `midi` 应为 `null`，仅静音该音，同时保留事件时值与定位。

当前 `playback-plan.ts` 仍然抛出 `RangeError`，异常会让整份播放计划进入 `unsupported`。这是已经确认的实现偏差，应作为独立小修复优先完成。

### P0-7 插件宿主 Projection 与内核引用生命周期

这两项共同前置条件必须分层完成：微内核实现通用引用生命周期；插件宿主实现可组合 Projection。Tie、力度、歌词、指法插件只提交各自的音乐规则，不能重复实现底层机制。

## P1：进入完整业务能力前补齐

### 1. 稀疏速度时间线

当前只有全局 BPM。需要按位置持续生效的速度变化，第一版可从小节起点变化开始，后续再扩展到拍内位置、渐快和渐慢。

速度时间线应由 Projection 以游标方式消费；播放计划必须按分段速度积分，不能继续使用一个 BPM 把全曲换算成秒。

### 2. 稀疏谱号变化

当前 Staff 只有 `defaultClef`，工作台修改的是整条 Staff 的初始谱号。需要 Staff 级稀疏谱号变化，并支持换谱号后的音高定位、系统开头重显和取消／继承。

### 3. 拍号分组与显示语义

当前数值拍号足以表达常规总时值，但不能表达：

- `3+2+2/8` 等加法拍号；
- 同一 `7/8` 的不同重音／连桁分组；
- `common time`、`cut time` 等显示形式；
- 用户指定的断桁和跨拍连桁。

这些信息应作为拍号或刻谱模块的语义，不要通过手工坐标保存。

### 4. 整小节休止与跨小节节奏重排

当前休止符只是普通有时值事件，没有“整小节休止”的独立记谱语义。在不规则拍号中，整小节静默不一定能用一个普通音值准确表达，刻谱规则也与同长度普通休止不同。

还需要受控的跨小节重排能力，用于改拍号、粘贴或主动整理超拍内容：

- `preserve-written-layout` 保留当前事件边界并只报告告警；
- `reflow-rhythm` 按时间顺序重新分配小节；
- 音符必须跨小节拆分时，通过 Tie 保持实际持续时间；
- 任何自动重排都必须预览影响范围并作为一个原子历史步骤。

这项能力不能替代当前宽容编辑；它是用户主动选择的整理操作。

### 5. Concert Pitch Projection

这是视图和导出投影，不是第二份持久化乐谱。切换时需要同步转换：

- 音符书写音高；
- 调号；
- 必要的等音拼写；
- UI 选择与播放定位。

切换视图不能修改原文档，也不能影响播放结果。

### 6. 力度和基础演奏法

至少需要：

- `pp` 到 `ff` 等基础力度；
- 渐强／渐弱范围；
- 重音、断音、保持音等常用演奏法；
- 播放 velocity／时值比例映射；
- 显示与播放策略可分离，原始音乐意图保持稳定。

它们适合作为第一方模块，内核只提供位置、范围、引用和事务机制。

### 7. 反复结构与播放路线

至少需要开始／结束反复、反复次数和第一／第二房。记谱事实与展开后的播放路线必须分开保存：文档保存反复结构，Playback Projection 生成有界路线并检测循环或矛盾结构。

### 8. 吉他基础事实

项目是吉他产品，但当前 Instrument 只有名称和 `writtenToSounding`。还缺：

- 弦数与每根弦的开放弦音高；
- 变调夹位置和局部变调夹边界；
- 弦号与品位；
- 同一音高的多把位选择；
- 乐器音域与可演奏性诊断；
- 书写音高、实际发声和指板位置之间的明确关系。

这些应由必装的 Guitar Foundation 第一方模块提供。通用微内核不应内置六弦吉他的规则。

### 9. 语义完整的复制粘贴

升级片段协议，使 Core 事件、模块关系、位置变化和 ID 重映射能一次导出／导入。复制范围跨小节、跨 Voice 时也必须有明确行为。

### 10. MusicXML 导入导出

当前原生项目文件、SVG 导出和 SoundFont 资源导入不能替代乐谱交换。商业基础互操作至少需要 MusicXML：

- 支持已实现能力的往返；
- 未支持内容保留或输出明确限制报告；
- 不允许静默丢失 Tie、Voice、调号、移调、力度等语义；
- 导入形成一个可撤销的新文档／替换操作，并经过相同验证边界。

### 11. 播放闭环扩展

Playback Projection 需要支持多 Part、多 Voice、和弦、Tie、弱起、连音组、速度变化、力度和反复路线。播放后端可继续替换，乐谱语义和播放计划不能绑定某个音源。

## P2：可以继续模块化扩展

以下能力重要，但不应阻塞第一轮基础音乐闭环：

- Slur（连奏线，与 Tie 分离）；
- 装饰音、倚音、颤音、回音、震音；
- 滑音、推弦、击勾弦、泛音等吉他技巧；
- 歌词与音节对齐；
- 和弦符号、和声分析、排练标记；
- 多小节休止；
- 自定义小节线、系统／页面换行提示；
- MIDI 乐谱导入导出与实时 MIDI 输入；
- 打击乐和无固定音高乐器；
- 微分音、自定义调号和非常规谱表；
- 复调跨谱表的高级刻谱覆盖；
- Guitar Pro 等专有格式导入。

其中某些能力对特定产品版本可能提前，但它们仍应通过模块接入，不扩大通用微内核。

## 职责边界

### 微内核负责

- 实体身份、顺序、范围和层级；
- 原子事务、历史、撤销重做和重放；
- Extension／Contribution 的权限、生命周期和资源预算；
- Module SDK／Registry 中引用声明的可信编译边界，以及 reconciliation 的原子执行；
- 通用 Batch、Effect、错误归因和受限读取；
- 未知扩展的无损保存和兼容降级；
- 为宿主提供稳定、受权限限制的只读快照和贡献执行结果。

微内核不保存 Tie、Slur、力度、歌词、指法、调号、反复等具体音乐对象，也不直接调用刻谱引擎或构造播放路线。

### 插件宿主／平台负责

- 装配第一方与第三方插件；
- 根据已验证的引用／触发声明选择 reconciliation，并显式组装原子 Batch；
- 组合 Notation、Playback、Clipboard 等插件投影；
- 隔离单个插件的视图故障，避免无关功能拖垮整份文档；
- 协调 fragment export/import、ID 映射和批事务提交；
- 将内核结构化错误映射成稳定的产品反馈。

### 必装第一方音乐模块负责

- Key Signature（已完成基础 V1）；
- Tie；
- Pitch Transformation 与拼写策略；
- Tuplet Group；
- Tempo Timeline；
- Clef Timeline；
- Dynamics／基础 Articulation；
- Repeat Route；
- Guitar Foundation。

这些模块负责自己的 schema、命令、校验、reconciliation 决策、投影和音乐规则。它们通过与第三方插件相同的 Kernel Effect／Contribution 合同运行。

### 可选插件负责

- Slur、歌词、和弦符号和各种高级记谱；
- 吉他技巧与智能指法；
- MusicXML／MIDI／Guitar Pro 等格式适配器；
- 高级播放、音色、混音和分析能力。

“第一方模块”与“第三方插件”的运行合同应相同。区别在发行、信任、默认安装和兼容承诺，不应给第一方模块绕过内核事务或权限边界的后门。

## 推荐实施顺序

1. **微内核收口**：保持冻结的 28 命令 V1，完成 Effect 双后端一致性和商业资源资格；Note 子项先复用 Event 原子替换，不加入和弦规则。
2. **插件平台收口**：基于引用／触发声明自动选择 reconcile 命令并显式组装 Batch；建立可组合 Projection 与语义 fragment 协议，取消“出现未知扩展就整谱 unsupported”的硬编码策略。
3. **宿主小修复**：按既定合同修复播放 MIDI 越界，使单音局部静音而非整谱失败。
4. **第一方插件验证机制**：实现 Tie V1，用它验证引用生命周期、Projection、播放和历史闭环；Tie 的业务代码不进入内核。
5. **第一方音乐插件**：实现 Pitch Transformation V1，补齐上一轮全部调性／移调缺口。
6. **工作台／记谱插件**：打通和弦与多声部，使用内核的通用 Note／Voice 结构命令。
7. **节奏插件与工作台**：打通弱起、完整时值、附点和 Tuplet Group。
8. **第一方插件**：增加 Tempo Timeline、Clef Timeline、Concert Pitch 和 Guitar Foundation。
9. **第一方／可选插件**：增加力度、基础演奏法、反复路线和语义剪贴板。
10. **格式与播放插件**：完成 MusicXML 和扩展后的播放闭环。

这个顺序先冻结通用内核机制，再完善插件宿主，最后增加音乐插件，可避免每个模块各写一套删除、复制和 Projection 特例，也避免音乐规则反向污染内核。

## 当前完成度评估

这是按能力闭环而非代码行数估算：

| 维度 | 当前估计 | 判断 |
| --- | ---: | --- |
| 微内核通用编辑机制 | 98%–99% | 核心功能机制已完整，Effect 双后端一致性已补齐；剩余主要是结构路径增量资格、长期稳定性、多平台和发布工程。自动选择 reconcile 与可组合 Projection 属于插件平台，不计入内核 |
| Core 最小结构事实 | 75%–85% | 音高、时值、Part／Staff／Voice／Event／Note 足以作为最小事实骨架；Tie、时间线和吉他语义不应计入 Core 缺口 |
| 第一方音乐插件能力 | 25%–35% | 当前主要完成调号 V1，Tie、Pitch Transformation、节奏关系、时间线和吉他基础仍待建设 |
| 工作台基础记谱闭环 | 35%–45% | 当前稳定范围仍是单谱表、单声部、单音和有限时值 |
| 商业音乐基础平台整体 | 45%–55% | 可以进入下一阶段开发，但第一方插件和产品闭环尚未完成；这不等于微内核只有一半完成 |

上述百分比不是测试覆盖率。它表示一个真实用户能否把常见乐谱从创建、编辑、播放、保存、复制到交换格式完整走通。

## 商业基础层完成门槛

在宣称“音乐基础层完成”前，至少应满足：

1. Tie、和弦、多 Voice、弱起、常用连音组能创建、显示、播放和保存。
2. 转调可选择拼写策略，并能原子联动音符与调号。
3. 速度和谱号支持稀疏变化，Concert Pitch 不复制事实。
4. Guitar Foundation 能表达定弦、变调夹、弦品和多把位。
5. 任意已安装音乐模块不会让无关基础 Projection 整体失效。
6. 删除、复制、撤销和重放不会留下悬空模块引用或静默丢失关系。
7. 播放对单个不可播放音高局部降级，不使整份计划失败。
8. MusicXML 对已支持语义可以往返，对未支持语义提供明确限制报告。
9. 所有新能力均有 TS／Rust 一致性、原子失败、历史和保存重开回归。

达到这些条件后，才适合把整个产品状态提升为“商业可用的基础音乐平台”。微内核自身可以在通用引用生命周期、子实体 CRUD 与相关可靠性验证完成后先行冻结；无需等待所有音乐插件完成。
