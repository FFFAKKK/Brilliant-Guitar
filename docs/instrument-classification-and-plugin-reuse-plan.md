# 乐器分类与插件复用计划

> 状态：**实施中（第一阶段完成）**
> 2026-09-19 已完成平台接口校准、品格弦乐族工厂、Guitar V1 迁移和统一吉他插件包注册。
> 当前族级 SDK 仍是内部接口；吉他已完成首批调弦/技巧行为；宿主执行绑定、通用技巧注册表、六线谱/控件和播放投影尚未完成。

## 1. 目标

在不向 Core Kernel 写入具体乐器知识的前提下，为吉他、贝斯、钢琴以及后续乐器建立一套可扩展的领域模型，使：

- 同族乐器共享结构、算法、校验、命令与投影，不复制整套模块；
- 不同族乐器只共享真正通用的音乐概念，不被迫套用吉他的品格模型；
- 新乐器主要通过“族实现 + 乐器 Profile + 技巧包”组合得到；
- 统一插件平台只负责通用插件机制，不反向依赖乐器领域类型；
- Core Kernel 继续只维护乐谱事实、事务、历史、回放与扩展块机制。

这与面向对象的抽象和继承目标一致，但运行时不采用深层类继承树。最终模型以**能力组合、带判别字段的族 Profile、可复用族级实现和显式注册表**为主，类继承只可用于局部实现，不成为公共数据协议。

## 2. 为什么不能只建一棵乐器继承树

乐器不存在唯一、稳定的分类树。同一乐器会同时落在多个维度上：

- 吉他是弦乐器、品格乐器、可移调或变调弦乐器、多声部乐器，也可能使用五线谱和六线谱；
- 贝斯与吉他共享弦与品格拓扑，但音域、弦数、记谱习惯和技巧集合不同；
- 钢琴与吉他都能演奏和弦，却不应继承弦号、品位、推弦等数据结构；
- 无品贝斯与有品贝斯共享大量语义，但音高定位能力不同。

若建立 `Instrument -> StringInstrument -> Guitar -> ...` 这样的单继承树，记谱、演奏拓扑、发声方式和技巧会被混在同一轴上，最终形成大量可空字段、类型判断和父类例外。

因此采用多轴分类，并把分类结果表达为能力：

| 分类轴 | 示例 | 用途 |
| --- | --- | --- |
| 物理/演奏拓扑 | `fretted-string`、`unfretted-string`、`keyboard`、`wind`、`percussion` | 选择族级数据结构和算法 |
| 音高行为 | 有音高/无固定音高、离散/连续、固定/可变调弦 | 决定音高映射与校验能力 |
| 声部行为 | 单音、多音、延音、复音上限 | 决定输入与播放约束 |
| 记谱能力 | 五线谱、六线谱、打击谱、和弦图 | 声明可贡献的投影，而非改变 Core 事实 |
| 演奏技巧 | 推弦、滑音、揉弦、踏板、气息、击法 | 通过独立技巧定义和技巧包组合 |
| 播放能力 | 音色、奏法映射、发音参数 | 贡献播放提示，不改写乐谱真值 |

分类用于选择能力和实现，不用于制造一个覆盖所有乐器的“大一统对象”。

## 3. 分层边界

```text
统一插件平台
  └─ 生命周期、清单、依赖、启停、冲突、诊断、设置、贡献点
       └─ 乐器领域 SDK
            ├─ 通用乐器描述与能力协议
            ├─ 技巧定义协议
            └─ 族级插件工厂
                 ├─ 品格弦乐族
                 │    ├─ 吉他 Profile + 技巧包
                 │    └─ 贝斯 Profile + 技巧包
                 └─ 键盘族
                      └─ 钢琴 Profile + 技巧包

Core Kernel
  └─ 乐谱事实、稳定 ID、事务、历史、回放、ExtensionBlock
```

### 3.1 Core Kernel

Core 不认识 `guitar`、`bass`、`piano`、弦、品、琴键或具体技巧。它只提供：

- 稳定乐谱对象和 ID；
- 原子命令/效果提交；
- 历史、撤销、重做和回放；
- 扩展数据的保存、归属和生命周期机制；
- 通用验证与失败隔离边界。

### 3.2 统一插件平台

平台负责所有插件共有的问题：

- 插件身份、版本、清单与依赖；
- 注册、发现、激活、停用和失败隔离；
- 能力声明和贡献点；
- 设置、诊断、冲突报告和权限；
- 命令、投影及 UI/播放适配的挂载通道。

平台不得导入乐器族类型，也不得出现 `if pluginId === guitar` 一类领域分支。

### 3.3 乐器领域 SDK

这是统一平台之上的消费者层，负责：

- `InstrumentDescriptor`：稳定身份、名称、族、记谱与播放声明；
- `InstrumentCapabilities`：多轴能力集合；
- `InstrumentProfile`：某件具体乐器的静态或可配置参数；
- `TechniqueDefinition`：技巧 ID、作用域、严格数据编解码、校验和投影；
- `defineInstrumentPlugin` 和各族工厂：把 Profile 与族实现组合成平台插件贡献。

领域 SDK 依赖统一插件平台；统一插件平台不依赖领域 SDK。

### 3.4 乐器族实现

每个族只拥有本族确实共享的模型与算法。例如品格弦乐族负责：

- 弦、开放弦定音、品位、变调夹；
- 位置到实际音高的映射；
- 弦数、品位范围、同音异位等校验；
- 通用位置命令、编解码和投影；
- 可选的滑音、推弦、揉弦等技巧定义或技巧包。

键盘族另有键位、键域、踏板等模型，不依赖品格弦乐结构。

### 3.5 具体乐器 Profile

具体乐器提供参数和能力选择，不复制族实现。概念上：

```ts
defineFrettedInstrumentPlugin({
  id: "brilliant.instrument.guitar",
  family: "fretted-string",
  strings: ["E4", "B3", "G3", "D3", "A2", "E2"],
  fretRange: [0, 24],
  notation: ["staff", "tablature", "chord-diagram"],
  techniques: [slide, bend, vibrato],
});

defineFrettedInstrumentPlugin({
  id: "brilliant.instrument.bass",
  family: "fretted-string",
  strings: ["G2", "D2", "A1", "E1"],
  fretRange: [0, 24],
  notation: ["staff", "tablature"],
  techniques: [slide, bend, vibrato, slap],
});
```

以上只是计划中的表达示例，不锁定最终 API 命名。

## 4. 复用规则

### 4.1 应抽象和复用的内容

- 插件身份、生命周期、依赖、启停、诊断；
- 技巧实例的稳定信封结构和版本策略；
- 族内的编解码、音高映射、校验、命令和投影；
- 乐器描述、能力声明、设置与播放提示的贡献方式；
- 未知插件数据的无损保存、撤销/重做和回放行为；
- 同族测试契约与测试夹具。

### 4.2 必须保留在具体乐器或技巧中的内容

- 默认定音、弦数、音域、键域等 Profile 参数；
- 某乐器支持哪些技巧以及技巧默认值；
- 技巧自己的严格字段、语义校验和表现方式；
- 乐器特有的记谱约定和播放映射；
- 不能被两个真实乐器共同证明的“预想抽象”。

### 4.3 禁止的复用方式

- 一个包含大量可空字段的 `UniversalInstrument`；
- 在共享引擎中按具体乐器 ID 写巨大 `switch`；
- 为了统一结构，让钢琴拥有虚构的弦/品字段；
- 把所有技巧内容降级为无约束 `JsonObject`；
- 每新增一种乐器就复制一套命令、编解码和校验；
- 让乐器插件覆盖 Core 的绝对音高、移调或乐谱事实。

## 5. 技巧模型

技巧分为“通用容器”和“插件拥有的严格定义”两层：

```ts
interface TechniqueInstanceEnvelopeV1 {
  techniqueId: string;
  schemaVersion: number;
  ownerPluginId: string;
  target: StableScoreReference;
  payload: unknown;
}

interface TechniqueDefinitionV1<TPayload> {
  id: string;
  schemaVersion: number;
  decode(raw: unknown): TPayload;
  encode(value: TPayload): unknown;
  validate(value: TPayload, context: TechniqueContext): Diagnostic[];
}
```

平台和通用 SDK 只理解信封、归属和生命周期；具体定义拥有 payload 的类型、迁移和语义。这样既允许跨乐器复用揉弦等技巧，也不会把推弦、踏板、呼吸等差异塞进中央联合类型。

技巧包只是定义集合，例如 `fretted-expression-pack`，具体乐器仍显式选择它支持的技巧，不因属于某族就自动获得全部能力。

## 6. 建议的逻辑包结构

最终物理目录须等统一插件平台交接后再确定，以下仅表达依赖方向：

```text
instrument-sdk/
  contracts
  capabilities
  define-instrument-plugin
  technique-definition

instrument-families/
  fretted-string/
    contracts
    codec
    pitch-mapping
    validation
    commands
    projections
    plugin-factory
  keyboard/
    ...

first-party-instruments/
  guitar/
    profile
    techniques
    plugin
  bass/
    profile
    techniques
    plugin
  piano/
    profile
    techniques
    plugin
```

Music Foundation 中的调号、速度、力度、连音等属于跨乐器音乐语义，不放入任何乐器族插件。

## 7. 实施入口门

统一插件平台交接后，逐项确认以下接口；任一实施阶段只能使用已经稳定的接口，不用临时旁路固化第二套平台：

1. 稳定的插件 ID、版本、清单和定义入口；
2. 乐器描述贡献点的最终形状与冲突规则；
3. 能力声明、版本协商与依赖排序语义；
4. 激活、停用、失败隔离和恢复语义；
5. 类型化命令、投影、设置和播放贡献通道；
6. 诊断与冲突报告接口；
7. 启动期目录冻结/应用装配规则，或与 Core 官方模块目录之间的明确适配层；
8. UI 插件与 Kernel Domain Module 的边界和 ID 映射规则；
9. 持久化扩展数据在插件缺失、禁用或升级时的保留与迁移契约；
10. 可用于自动化测试的平台宿主夹具。

### 2026-09-19 入口复核结果

- 已确认：`definePlugin()` 统一包入口、插件/乐器 ID 校验、乐器描述贡献、固定会话 Kernel Module 清单、启动前冻结、冲突诊断、失败隔离和测试宿主；
- 已确认：平台只生成数据化 Kernel 装配计划，可信宿主单独绑定真实实现，平台不执行或解释 Guitar 代码；
- 因此允许启动内部 first-party 的 P0/P1/P2/P4 重构，并注册吉他清单；
- 尚未宣称完成：桌面与浏览器宿主的真实模块绑定、吉他命令的 UI 投影/写端口、六线谱交互、技巧控件和播放奏法映射，这些继续受 P3/P6 质量门约束。

## 8. 平台完成后的实施阶段

### P0：契约校准

- 根据平台最终 API 修订本文名词和依赖图；
- 用吉他、贝斯、钢琴三个对照样本验证多轴分类；
- 形成 ADR，冻结公共 ID、版本与兼容策略；
- 明确当前 Guitar Domain V1 原型中哪些行为保留、哪些结构废弃。

交付物：契约文档、ADR、三种乐器的只读 Profile 夹具。此阶段不迁移业务代码。

当前进度：平台边界与吉他/贝斯对照已校准；钢琴对照和独立 ADR 仍待后续阶段。

### P1：最小乐器领域 SDK

- 实现描述、能力、Profile、技巧定义和插件工厂的最小契约；
- 建立能力注册表，避免中央具体乐器分支；
- 建立契约测试，验证插件平台与领域层的单向依赖。

当前进度：已建立内部 `defineFrettedInstrumentDomainV1()` 契约和平台侧数据化 Guitar package；更高层、跨乐器族的能力注册表尚未建立。

### P2：品格弦乐族

- 提取调弦、弦/品位置、变调夹、音高映射和族级校验；
- 由同一工厂生成吉他和贝斯插件；
- 使用两种真实乐器证明复用，不为尚不存在的变化过度抽象。

当前进度：调弦、弦/品位置、变调夹、音高映射、命令、效果、校验和目录装配已提取；使用四弦 Bass fixture 证明复用，尚未发布正式 Bass 插件。

### P3：技巧注册与技巧包

- 把技巧的编解码、校验、迁移和投影注册化；
- 提取可共享的滑音、揉弦等定义；
- 保持推弦、击弦等乐器支持范围显式可见；
- 验证未知技巧和禁用插件时的数据无损行为。

当前进度：吉他内部严格技巧适配器已覆盖 `hammer-on`、`pull-off`、`slide`、`bend`、`vibrato`。跨乐器技巧定义注册表、技巧包、应用能力入口和未知技巧保留仍未完成。

### P4：迁移 Guitar Domain V1

- 将冻结原型迁移到族工厂和 Profile；
- 保留已有原子音高+位置事务语义；
- 为已有 ExtensionBlock 决定兼容、迁移或明确废弃策略；
- 删除迁移后确实重复的吉他专属基础设施。

当前进度：已完成。既有命令 ID、namespace、schema、原子音高+位置事务和行为测试保持不变。

### P5：键盘族与钢琴

- 实现独立的键盘拓扑和踏板等能力；
- 只复用乐器 SDK、技巧协议和平台贡献机制；
- 以钢琴验证架构没有被品格弦乐过拟合。

### P6：宿主集成

- 通过统一平台接入记谱、播放、设置与 UI 投影；
- 不允许 UI 直接解释私有 ExtensionBlock；
- 验证插件启停、失败、冲突和恢复路径。

### P7：兼容与质量门

- 完成 round-trip、撤销/重做、回放、迁移、未知插件和禁用插件测试；
- 建立新增乐器与新增乐器族的模板和契约测试；
- 性能与诊断达标后，才把 SDK/持久化结构标记为稳定。

## 9. 每阶段的停线条件

出现以下任一情况，停止扩展并回到抽象边界复核：

- 共享实现需要判断具体 `guitar`、`bass` 或 `piano` ID；
- 新乐器必须复制同族的编解码、命令或校验才能接入；
- 钢琴等新族被迫填充无意义的弦/品字段；
- 通用平台被要求理解某一乐器技巧的 payload；
- 持久化格式先于所有权、版本和迁移策略落地；
- 插件停用或缺失会导致原始乐谱扩展数据丢失；
- 平台最终接口仍在变动，却需要用临时适配层继续堆业务实现。

## 10. 完成判定

只有同时满足以下条件，才认为“乐器分类与复用层”完成：

- Core Kernel 和统一插件平台均不导入具体乐器领域类型；
- 吉他和贝斯共享全部品格弦乐基础设施，差异主要由 Profile 与技巧选择表达；
- 钢琴复用通用乐器契约，但完全不依赖品格弦乐数据结构；
- 同族新增乐器以 Profile、技巧选择和测试为主，不复制模块骨架；
- 新增乐器族不需要修改已有族实现；
- 不存在按具体乐器 ID 分派的中央巨大条件分支；
- 每个持久化扩展 ID、schema 版本、所有者和迁移策略明确；
- 原子事务、round-trip、撤销/重做、回放、投影、插件启停、未知插件与迁移测试全部通过。

## 11. 当前实施决定

- 继续保持 Core Kernel 对具体乐器零依赖；
- 六弦、标准调弦和 Guitar 技巧联合类型只存在于 Guitar Profile/adapter，不提升为族级通用协议；
- 统一插件平台只持有乐器描述与 Kernel Module 清单，不解析私有 ExtensionBlock；
- 品格弦乐族工厂作为内部复用层，待正式 Bass 插件再次验证后再考虑稳定公开；
- 下一阶段优先完成 P3 技巧注册表和 P6 可信宿主绑定，不提前实现钢琴或制造统一大对象。
