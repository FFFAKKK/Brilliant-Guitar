# 保留扩展对象键顺序与编码兼容

2026-09-14，改动前基线 `1218a67`。

## 问题与修复

原 Rust JSON 对象及扩展 payload 使用 `BTreeMap`。解码时就按键排序，
原始插入顺序随即丢失。即使音符和扩展值完全恢复，
`encodeScoreDocumentJson` 仍产生不同字节，冻结代表性前置检查因此失败。

另一个实际差异是独立插件编辑的 no-op 判定：TS SDK 的 `deepEqual`
按 `Reflect.ownKeys` 的顺序比较扩展，而 Rust 原先只比较映射中的键和值。
仅调整扩展键顺序的写入可能被 Rust 错误丢弃。

本轮实现：

- `JsonObject` 用顺序条目保存值，用 `BTreeMap` 保存键到位置的索引。
  读取与重复键检查保持索引查找；替换已有字段保持位置，
  删除后重新插入则追加。没有新增依赖或 unsafe。
- Foundation 与 Contracts 捕获、强类型 DTO、Store 扩展记录、变更集
  以及普通输出使用该容器，顺序随数据进入历史和快照。
- 普通协议对象比较仍忽略字段顺序；扩展 DTO、Store 记录及重放
  前置条件使用递归的顺序比较，与现有 SDK 的扩展语义一致。
- 专门的 `write_lossless_json` 和 `canonical_score_bytes` 继续执行旧的
  规范化键排序。普通 DTO 的 `LosslessEncode` 保留插入顺序。没有通过修改
  冻结输入、哈希规则或比较对象来让资格前置检查通过。
- 冻结的 Core V1 snapshot / shared document 输出明确调用流式规范化
  编码器，保持旧 Native 读取与 P3B 消费者的字节契约。集成 Runtime
  两种 read 请求均明确输出原始顺序，避免通过旧 snapshot 编码器
  再次排序。不能把集成路径的保序能力泛化为 V1 快照行为也已改变。
- ExtraField 的首个诊断仍按原来的词典序选择；字节、深度、属性数、
  读取与插件资源限制保持不变。

私有 Rust crate 的 opaque object 类型由 `BTreeMap` 改为 `JsonObject`；
这是内部表示调整，公开 TS 入口和数据格式未新增字段。
`JsonObject::remove_entry` 需移动后续条目并更新位置，成本为 O(n)；
当前结构解码在字段数固定的对象上使用它，任意宽 payload 不按字段拆除。
保持顺序需要额外的条目向量与索引键存储，不能假定内存开销免费。

## 验证设计

- 5,000 步确定性插入、覆盖、删除与重插序列，对照独立 Vec 模型，
  每一步检查完整顺序与所有键的查询结果。
- 验证普通映射等价与扩展顺序等价的区别，包含嵌套对象、数组、
  UTF-16 非标量键，并分别比较保序输出与旧规范化输出。
- Native/Wasm 对照 TS 的完整编码字符串，覆盖数字样式键、
  `__proto__`、孤立代理项、负零和未知扩展。
- 同一插件写入只改变键顺序时必须提交，完全重复时必须 no-op；
  比较编辑、撤销、重做、历史与事件，输入对象保持不变。
- 新 Native 测试先在旧产物复现失败，再在重建产物通过。
- 旧规范化规模证据继续比较所有字段的语义值与两次规范化字节；
  用明确的语义比较替代现在包含扩展顺序的 DTO `Eq`。对应源码审计
  断言同步调整，冻结语料、计数、性能阈值与历史证据未改动。

本轮重建 Core、Integrated 与 Wasm 三种 Native addon，以及 CVN-7
参考 guest。历史 `guest.wasm` / `guest-v2.wasm` 保持原产物。
CVN-7 guest 从最终源码重复构建，SHA-256 均为
`3d43b6dfa2cd4d013f01b8e69a7d7c10440a39cad27bf58d12e23908a410a774`。

旧 Native 与 CVN-7 guest 备份在 `target/ordered-json/`。
普通 Integrated 旧文件被既有 Node 进程占用，校验与备份一致后将其
原地移到 `target/ordered-json/active-prior-integrated.node`，再安装新产物。
该进程继续使用已加载的旧版本；新进程使用新文件，没有终止现有开发进程。

  单独运行 1 通过。Node 完整回归 892 通过、2 跳过、0 失败。
- fmt、严格 Clippy、Rust 1.88 最低版本检查、TS 严格类型检查与构建通过。
  Core V1 的 UTF-16 键规范化测试和 P3B 固定输出哈希检查保持原断言并通过。
- 最终三种 Native 产物完成后，依次在新进程运行两种冻结前置检查；
  性能取样期间没有并行构建或测试。

撤销 290.44 ms，重做 293.68 ms，缓存读取 0.20 ms。
进程峰值 RSS 为 447,897,600 字节。

压力规模（102,400 事件、51,200 音符）构造与原始编码检查通过，

两者均是每操作单次诊断样本，明确保留 `qualification: false`；
耗时不能作为 p95/p99，峰值 RSS 包括语料生成和正确性检查。

## 商业边界

修复的是数据保留、no-op 和编码兼容。它不解决 6,401 条功能提示与
4,096 条报告上限的冲突，也不消除全量候选投影/校验。
商业性能资格、长序列压力测试、真实插件/UI 集成与默认切换仍需完成。
