# 相邻历史状态的 Core 分类复用

日期：2026-09-16。

## 目标

Integrated Runtime 的撤销与重做会回到刚刚离开的相邻提交状态。此前即使
该状态的完整 Core 功能分类已经成功发布，历史切换仍会重新扫描整份文档。
本轮消除这一项确定性的重复工作，同时保持语义校验、插件校验、事务原子性
和公开返回值不变。

## 实现边界

Runtime 只保存两个派生结果：当前已提交版本的 Core 分类，以及一个相邻
历史状态的 Core 分类。相邻项使用 journal 的稳定 history identity 绑定，
不能仅凭持续增长的 documentVersion 猜测状态。

- Core、模块或 Batch 成功提交且确实改变文档时，原当前分类移入相邻槽位。
- undo/redo 只有在目标 history identity 精确匹配时才复用相邻分类。
- 历史切换成功后，刚离开的当前分类成为新的相邻项，从而支持反向切换。
- 候选拒绝、历史为空、身份不匹配或没有已发布分类时不采用缓存。
- 缓存固定为一个相邻项，不随 undo 栈或 redo 栈增长，也不保存第二份文档。

复用的只有 K1 功能分类。每次仍执行完整 Core 语义校验、资源边界检查、
模块验证与模块分类。插件拒绝仍发生在采用历史状态之前；失败不会移动游标、
增加版本、发布事件或污染当前及相邻缓存。

## 验证

Rust 定向测试使用内部扫描计数验证：一次真实 Batch 建立两个已发布分类后，
undo 与 redo（包括先由插件拒绝、再重试成功）均不增加 Core 分类扫描次数；
拒绝前后的文档版本、历史投影和两个缓存保持一致。

本轮验证结果：

- `cargo +1.97.1 test --workspace --all-features --locked --offline`：
  607 通过、1 忽略、0 失败；其中 Runtime 为 359 通过、1 忽略。
- 严格 Clippy（全部目标、全部功能、`-D warnings`）通过。
- Rust 1.88 MSRV 全部目标、全部功能检查通过。
- 重建 Core V1、Integrated V2 与 Wasm V1 三套 Node 原生产物。
- 六个关键 Node/Native/Wasm 测试文件：81 通过、0 跳过、0 失败；其中使用
  `--expose-gc` 实际执行了默认环境下跳过的 FinalizationRegistry 生命周期用例。
- 完整 `npm test`：894 通过、2 跳过、0 失败。两个跳过分别由
  `node --expose-gc` 和 `BRILLIANT_RKP2_RUN_SCALE_E2=1` 显式开启；后者是
  102,400 事件的独立 Stage 6 E2 私有规模流程，不属于普通回归默认负载。

## 性能证据及限制

在 25,600 事件代表性夹具上，单个全新进程完成构造、真实 Wasm 混合 Batch、
undo、redo 及逐步哈希校验。公开操作单样本为：

| 操作 | 耗时 |
| --- | ---: |
| submit-batch | 905.90 ms |
| undo-batch | 734.35 ms |
| redo-batch | 649.98 ms |

这组数字只证明完整路径能在限定时间内完成，不能证明稳定提速。与历史单样本
相比存在正常运行波动，因此本轮不宣称百分比性能改善。内部计数能够证明被
删除的分类扫描确实没有执行，但指标仍显示每次历史切换执行约 20.5 万条语义
规则和 60.3 万次语义依赖读取；完整语义校验仍是主要成本。

原始输出保存在
`docs/evidence/adjacent-history-classification-representative-2026-09-16.json`，
其中包含 addon、脚本和 guest 哈希、操作耗时、RSS、夹具计数与测试限制。

商业性能后续重点是增量语义校验与依赖失效、正式 p50/p95/p99 采样、长序列
内存与故障恢复，以及真实业务插件和桌面 UI 的端到端容量验证。本轮没有改变
默认发布选择，也没有把单样本诊断描述为商业资格通过。
