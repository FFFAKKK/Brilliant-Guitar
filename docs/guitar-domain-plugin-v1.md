# Guitar Domain Plugin V1

> 状态：**V1 领域实现已迁移到品格弦乐族工厂，并已注册统一插件包**。稳定命令 ID、Extension namespace 和 schema `1` 保持兼容；族级 SDK 仍是内部演进接口，不承诺第三方兼容。后续阶段见[乐器分类与插件复用计划](./instrument-classification-and-plugin-reuse-plan.md)。

## Purpose

`brilliant.instrument.guitar` is the first production first-party instrument
module. It proves that the generic kernel can host real guitar semantics without
adding tuning, fret positions, or techniques to the Core score schema.

The V1 vertical slice owns:

- explicit six-string tuning as sounding pitches;
- standard, Drop D, DADGAD, and Open G tuning presets plus an atomic tuning command;
- fret count and capo position;
- one string/fret placement per referenced Core Note;
- `hammer-on`, `pull-off`, `slide`, `bend`, and `vibrato` technique instances;
- semantic commands, validation, support classification, history, replay, and
  lossless score persistence through one Part-owned ExtensionBlock.

The concrete Guitar file now owns only its data profile and strict technique
semantics. Shared tuning/position codecs, pitch mapping, commands, effects,
validation, catalog assembly, and persistence lifecycle are generated by the
fretted-instrument family factory. A four-string fixture proves that the family
implementation is not keyed to the Guitar plugin ID or six-string topology.

## Stable identities

| Kind | ID |
| --- | --- |
| Extension/module | `brilliant.instrument.guitar` |
| Initialize command | `brilliant.instrument.guitar.initialize` |
| Tuning command | `brilliant.instrument.guitar.set-tuning` |
| Position command | `brilliant.instrument.guitar.set-position` |
| Technique upsert | `brilliant.instrument.guitar.set-technique` |
| Technique removal | `brilliant.instrument.guitar.remove-technique` |
| Extension schema | `1` |

The default tuning is persisted as six explicit pitches, not as an `EADGBE` or
`standard` label: `1=E4, 2=B3, 3=G3, 4=D3, 5=A2, 6=E2`.
Preset IDs are discovery/input conveniences; executing a tuning change persists
the six explicit pitches. See [the research and V1 scope](./guitar-first-party-plugin-research-v1.md).

## Transaction boundary

Setting a fret position emits an ordered Core written-pitch effect and a
Guitar-owned extension effect. The kernel assesses and commits both together,
so one user action creates one history entry and cannot leave pitch and
fingering out of sync.

Changing tuning similarly rewrites every positioned Note's derived written
pitch and the Guitar-owned tuning in one transaction. Undo, redo, reopen, and
replay therefore observe one coherent tuning state.

Technique and position references are validated against stable Core Note IDs.
A referenced Note cannot be removed by a standalone Core command. The caller
must remove its Guitar relationships and the Core entity in one atomic batch;
undo restores the whole relationship graph.

## Technique contracts

- `hammer-on`: a forward same-string pair whose destination fret is higher;
- `pull-off`: a forward same-string pair whose destination fret is lower;
- `slide`: a forward source/destination Note pair on the same string and different frets;
- `bend`: one Note plus a discrete one- or two-semitone target;
- `vibrato`: one Note with the basic V1 display/playback semantic.

Each kind has a fixed category, P0 priority, Note target, display semantic, and
playback semantic in `GUITAR_TECHNIQUE_DEFINITIONS_V1`. User-visible names stay
in product i18n rather than persisted score data.

## Current limits and next boundary

- V1 initializes standard tuning, 24 frets, and capo 0. Tuning is editable via
  explicit pitch arrays and four first-party presets; a capo editing command is
  still a later slice.
- Written pitches derived from frets use deterministic sharp spelling. Key-aware
  enharmonic spelling belongs to a later Pitch Transformation collaboration.
- Chords are accepted by the Guitar domain; simultaneous placements still must
  use distinct strings.
- The unified plugin package publishes the same `brilliant.instrument.guitar`
  identity as both an instrument contribution (`fretted-string`, staff and
  tablature) and a fixed-session Kernel Module manifest. The generic platform
  validates and freezes this plan without interpreting Guitar payloads.
- The trusted Product Host still has to bind the data-only package plan to the real
  TypeScript/Rust implementation. Tablature, technique controls, and playback
  projections remain separate integration work.
- General reference declarations and automatic reconciliation are still a
  kernel evolution item. V1 stays safe by rejecting dangling candidates and by
  requiring explicit atomic cleanup batches.

## Verification

`test/core-kernel/guitar-domain-module.test.ts` covers initialization, atomic
pitch/position/tuning updates, the five techniques, malformed input, relationship
cleanup, undo/redo, save/reopen, and replay. The first-party catalog test proves
that Guitar Domain and Key Signature assemble in the same frozen catalog.
`test/core-kernel/fretted-instrument-domain.test.ts` proves reuse with a
four-string profile, and `apps/workbench/test/guitar-plugin.test.ts` proves the
unified package identity, instrument discovery, and Kernel assembly plan.
