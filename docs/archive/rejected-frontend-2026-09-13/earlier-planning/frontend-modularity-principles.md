# 前端模块化设计原则

日期：2026-09-13。用户要求将谱面模块化思路推广到前端的大部分功能，便于管理、复用、扩展和审查。本文记录设计原则；尚未实现通用前端插件平台，也不创建或启动 Trellis 任务。

## 1. 总体方向

以职责明确的模块组织前端，通过明确的接口和依赖组合。基础工作台协调上下文和通用操作，谱面、领域输入、工具、输出等各自承担相关能力。模块化是否有效，应看修改能否局限在合理范围、能否独立理解和验证、组合后能否完成真实任务。

分开三个层次：

- 普通组件：按钮、输入框、对话框等，按组件接口复用。
- 功能模块：围绕一种完整职责组织组件、状态和服务，例如标准记谱视图或文件操作协调。
- 扩展贡献：需要由其他开发者新增或替换的能力，通过宿主定义的接入合同注册，例如另一种谱面、输出格式或分析工具。

模块不必都能运行中安装或卸载，也不必单独成为一个发布包。只有实际需要被替换或扩充的边界才设计扩展入口；不把每个按钮、工具函数和私有组件都做成插件。

## 2. 依赖、状态与操作归属

- 模块暴露明确入口，不直接依赖另一个模块的私有文件或私有状态。依赖通过宿主提供的受控能力或公开合同表达。
- 一个能力可以组合多种贡献，例如吉他同时提供领域规则、六线谱与输入适配；不要求一个插件只能贡献一个面板。
- 文档及其历史由内核统一管理；光标、选区、视口和临时输入按既有 UI Session 归属协调。视图自己的布局缓存可以局部持有，但不能成为另一份可独立修改的音乐事实。
- 修改音乐通过应用语义动作进入内核；界面、快捷键和菜单共享同一操作与可用性规则，不各自拼一套写入逻辑。
- 读取和通知传递明确的文档/对象身份与版本，避免跨文档或过期结果误作用。输入输出、错误、取消及资源结束规则由接口说明。

## 3. 有类型的接入点

谱面、工具面板、命令、设置项和输出提供方可以各有适合的注册合同，不使用一个任意对象/任意回调的万能接口掩盖职责差异。下面是扩展方向，不是首轮必须实现的 API 清单。

| 能力 | 合同关注点 |
|---|---|
| 谱面视图 | 适用内容、显示、命中定位、共享选区映射、可选输入能力与实例生命周期 |
| 命令及上下文动作 | 所需能力、目标、可用条件、语义效果和结果反馈 |
| 工具面板 | 文档/对象上下文、显示位置约束、关闭与资源清理 |
| 设置项 | 值类型、作用范围、生效时机、默认值和复位规则 |
| 输出提供方 | 输入快照、支持范围、参数、进度、取消和结果 |

身份冲突、必要能力缺失、未知版本和模块失败应有明确结果，不静默覆盖或宣称成功。第一轮允许启动时固定装配，动态发现、热更新和第三方执行隔离在有真实需求时另行设计。

默认五线谱与未来六线谱使用同一类接入合同；官方模块也使用对外扩展所需的入口。首轮可以是内部试用合同，经过第二个真实使用方验证后再决定公共版本，避免过早承诺永久兼容。

## 4. 便于他人使用与审查的最低要求

每个功能模块清楚记录：用途和边界、公开入口及使用示例、依赖和数据归属、错误及生命周期、针对合同的验证。对外接口变化说明兼容影响；代码目录与这些职责对应，而不是只按文件后缀分类。

测试既覆盖模块行为，也保留跨模块的真实流程。谱面独立画得正确不能替代输入、提交、撤销、保存重开的集成验证。无需为每个低风险样式改动建立一套额外测试或审核仪式。

## 5. 当前落实范围

第一阶段只落实基础 UI、五线谱模块、最小谱面注册入口，以及连接现有内核与文件服务的应用边界。先跑通直接输入、修改、撤销与保存重开。

第二阶段通过吉他领域与六线谱适配检验这些边界，再根据实际问题修订合同。其他扩展入口保留职责方向，不提前实现空的管理界面或全部注册系统。

具体输入、渲染及分阶段验收见 [最小 UI 方案](minimal-ui-input-rendering-plan.md)。
