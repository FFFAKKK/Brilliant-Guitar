# 初版 UI：直接输入与绘谱方案

日期：2026-09-13。继续直接规划与实现，不创建或启动 Trellis 任务。

通用设计依据：[前端模块化设计原则](frontend-modularity-principles.md)。本文件落实其中的首个真实切片，不要求先实现全部扩展设施。

## 最新分层与制作顺序

用户明确要求先做基础 UI 与基础五线谱，吉他业务插件完成后再接入吉他 UI；并提出通过通用谱面注册接口扩展新的谱面类型。本轮按这一顺序收敛，下面的品号输入和双谱验证移到第二阶段，不再作为第一阶段依赖。

1. 第一阶段：基础 UI 外壳、最小谱面注册机制、默认装配的五线谱模块、真实 Core 编辑及保存重开。先完成单小节、固定四分时值的标准音符/休止闭环；直接输入音高、删除及撤销重做不依赖吉他语义，具体键位在该小界面中确定，不增加逐音确认步骤。
2. 第二阶段：最小吉他领域模块提供弦品规则与数据；吉他 UI 适配通过同一注册机制提供六线谱和数字品号输入，并验证与五线谱对齐及共享编辑结果。
3. 后续：按真实需求扩充谱面类型、记号和复杂排版，用第二种真实视图暴露的问题完善接口，不在第一阶段预建完整插件平台。

五线谱采用独立、默认随应用装配的模块，也使用公共的谱面注册入口。它在产品上属于开箱可用的基础能力，在代码中不写死进 UI 容器。无需用户手工安装基础五线谱。

## 已确定的输入方向

用户明确希望快速直接输入，不接受每次输入后再按 Enter 或点击确认。这一原则适用于初版五线谱与后续吉他输入。以下品位规则针对第二阶段六线谱；此前提出的“品位输入框 + 确认操作”撤回，沿用原设计的谱面直接数字输入。

- 点击谱面或键盘导航确定当前编辑位置；谱面获得焦点即可输入数字。
- 按键立即显示当前位置的输入候选，自动完成输入收口、校验与提交，不要求额外确认。
- 两位数品号使用非阻塞短输入窗口，例如连续输入 1、2 形成 12 品。候选属于编辑会话；最终通过一个语义命令提交，形成一个撤销步骤。
- 新建音符成功后按已有设计前进；修改已有音符成功后保留该对象的选择。
- 导航离开当前目标时先收口候选，再移动；非法两位数组合不静默拆成两个位置的输入。失败保留原有效文档并在目标附近反馈。
- Esc 可以取消尚未提交的候选；已提交结果使用撤销恢复。文本框或命令搜索获得焦点时，数字归相应控件。
- 短窗口时长、快速连续单数字与两位数的区分体验在原型中实测，不把未经验证的毫秒值写成合同。等待识别第二位数字不等于等待用户确认，候选应立即可见。

以上继承原设计 `design.md` 的 A3/A4 输入边界，修正近期说明中的确认步骤；当前没有实现或时延测试结果。

## 绘谱方案建议

建议复用成熟绘谱库，自己实现编辑交互与内核适配。第一版优先验证 VexFlow，alphaTab 作为对照候选；这不是已经通过性能、全部技巧支持或长期扩展性验收的技术定案。

| 候选 | 官方资料可确认的能力 | 对本项目的判断 |
|---|---|---|
| VexFlow | TypeScript 乐谱与吉他六线谱绘制，SVG/Canvas 输出，MIT 许可 | 适合以本项目文档为基础生成显示对象；我们承担编辑交互、命中定位及应用级布局组织 |
| alphaTab | 五线谱/六线谱、多种输入格式、音频、自己的数据模型与 renderScore API，MPL-2.0 许可 | 吉他功能较完整；需要验证文档投影、对象身份、重绘与自定义交互的适配成本，不能简单视为不可编辑的查看器 |
| OpenSheetMusicDisplay | 基于 VexFlow 的 MusicXML 渲染；官方明确不是完整交互编辑器 | 对 MusicXML 展示较合适，本次直接编辑主路径暂不优先 |

官方来源（本轮已查阅）：

- VexFlow：<https://github.com/vexflow/vexflow>
- alphaTab 简介：<https://docs.alphatab.net/docs/introduction>
- alphaTab 功能与许可：<https://docs.alphatab.net/>
- alphaTab 渲染 API：<https://docs.alphatab.net/docs/reference/types/alphatabapi/>
- OSMD：<https://github.com/opensheetmusicdisplay/opensheetmusicdisplay>

## 各阶段的具体连接方式

用户进一步提出：基础界面提供五线谱，加入吉他插件后才获得六线谱，其他乐器插件可以提供对应专属记谱。建议采用这一能力分工，按下节区分基础 UI、领域贡献与显示选择。

第一阶段独立验证基础五线谱的显示、最小输入编辑、撤销与保存重开。第二阶段在已装配吉他插件且当前为适用吉他声部的配置下，验证同一小节上下对齐的五线谱与六线谱，在六线谱完成品位输入，五线谱同步显示音高与节奏。复杂分页和完整五线谱输入系统后续完善，不能以暂缓完整输入系统为由交付只能看、不能编辑的第一阶段 UI。

数据路径：谱面按键 → 对应视图的输入解释与编辑会话 → 应用语义命令 → Rust 及已装配领域规则验证与提交 → 读取有效文档 → 已注册谱面适配 → 当前视图显示。第一阶段不依赖吉他领域，第二阶段加入吉他规则与双谱视图。

同一个音乐事件以稳定 ID 关联两种谱面。渲染库的数据对象属于可重建的显示投影，不成为第二份音乐文档或撤销历史。撤销、保存、打开均由现有宿主与内核路径控制。

开源库负责已有的符号、谱线及其支持的排版能力；我们负责光标、选区、数字输入、两位数识别、命中映射、错误反馈，以及文档到渲染对象的转换。应用级换行、局部更新和高级技巧支持仍需逐项验证，不能假定安装库后已全部解决。

## 基础记谱与乐器扩展

“无插件时显示五线谱”在当前建议中指没有加载乐器扩展、但已加载基础 UI 与标准记谱能力；纯内核不负责绘图。基础 UI 本身未来是否作为可替换插件打包，不影响这一职责分工。

| 组成 | 负责内容 |
|---|---|
| 基础 UI 外壳 | 谱面容器、导航、共享选择、基础操作入口及统一反馈 |
| 默认五线谱模块 | 标准记谱渲染与命中映射、对应的基础输入适配；通过同一谱面注册入口装配 |
| 吉他领域贡献 | 标准调弦、弦品数据、音高一致性、适用性和合法性校验 |
| 吉他 UI 贡献 | 六线谱视图、弦/品命中定位、快速品号输入及后续专属控件 |
| 应用宿主 | 按能力及当前对象组织视图，共享选区、命令、历史、文件与生命周期 |

吉他领域与 UI 贡献可以作为同一个产品插件交付，但模块依赖分开：进入内核 SDK 的领域代码不依赖 DOM 或绘谱库，六线谱适配在 UI 侧调用绘谱能力。第一轮固定装配即可验证，不为此建设运行中热安装或完整插件市场。

宿主面向记谱视图能力组织界面，不写成“遇到名为 Guitar 的插件就画六条线”的特判。最小接入需要明确视图身份、支持的对象/数据版本、所需领域能力、渲染与命中定位、可用输入动作、订阅及销毁责任；不在本轮冻结完整公共插件 API。

### 最小谱面注册约定

这是 UI 宿主自己的视图注册机制，与内核现有 command/selector/domain 注册合同分开。可暂用 `registerScoreView` 表达接入概念，名称与 TypeScript 签名在实现时收口；不扩充冻结的 Core 导出。

| 注册内容 | 用途 |
|---|---|
| 稳定身份、显示名称和来源 | 宿主列出可用视图；同一身份重复注册应明确拒绝，不静默替换 |
| 适用对象与必要能力 | 判断当前声部/文档能否使用此视图，不要求所有声部使用相同谱面 |
| 实例创建、更新与销毁 | 在宿主提供的容器和受控上下文中绘制，及时清理订阅和资源 |
| 语义位置与屏幕位置的映射 | 将点击返回为事件/音乐时间/相关弦等目标，并将共享选区投影回视图；不把 DOM 节点当业务身份 |
| 可选输入与编辑能力 | 把数字、音名或手势解释为适用的应用动作；纯展示视图不必实现完整编辑器 |

宿主拥有文档会话、统一选择与焦点协调、命令调度、撤销和保存。视图提供具体的排版与命中规则，并声明是否支持某种输入；插件不自己维护第二套文档或历史。五线谱和六线谱要联合显示时，适配层需提供共同事件/音乐时间与布局位置的对应信息，以验证横向对齐；仅有任意 `render()` 回调不足以保证同步。

绘谱库封装在对应模块或共享适配器内，注册合同不把 VexFlow 对象作为公共音乐数据。五线谱与六线谱起步可以复用同一绘谱库；以后提供方可换实现，但仍须满足目标映射、布局协调与生命周期要求。

六线谱是带语义和交互的谱面类型。颜色、字号、谱线粗细属于已有视图的显示配置；未来只新增一个技巧符号时也可扩充已有视图，不必每次注册整套新谱面。首轮只实现五线谱实际需要的上述约定，第二阶段以六线谱检验通用性。

安装插件表示某种记谱能力可用，不等于对所有声部强制展示。最终显示取决于：能力已加载且依赖满足、当前声部/文档数据适用、用户显示选择。推荐吉他新谱初始显示五线谱与六线谱，用户可切换仅五线谱、仅六线谱或同时显示。其它乐器可以贡献独立视图，也可以复用/补充标准记谱；不要求每种乐器都有一套新谱。

通用音高文档不一定已经具备唯一弦品分配。仅安装吉他插件不能凭空把音符视作已拥有确定指法；转换为吉他声部时，由领域操作建立调弦与弦品数据，具体分配策略另行设计。

已有吉他作品缺失吉他插件时，保留原扩展数据，明确哪些专属内容不能显示或编辑；不能以隐藏六线谱为由放行破坏弦品/音高关系的通用修改。可安全读取时提供有缺失提示的只读基础预览，否则说明无法打开。主线交接记录表明依赖缺失的自动降级组装尚未完成，因此这是目标策略，实际接入要验证，不宣称现有内核已经自动支持。

## 最小验证

### 第一阶段：基础 UI 与五线谱

1. 通过注册入口装配默认五线谱模块；不加载吉他插件也能启动、显示通用文档并执行基础操作。
2. 在真实 Native 会话中完成新建一小节、直接输入音符、修改音高、删除恢复休止、撤销与重做，核对显示与内核读回。
3. 保存真实文件，重启宿主后重开并继续编辑；拒绝无效输入和保存失败时保留有效内容并反馈。
4. 视图重绘/重新挂载后目标映射正确、共享会话保留且无重复订阅；重复视图身份和不适用视图给出明确结果。

### 第二阶段：吉他业务与六线谱适配

1. 通过相同注册入口加入六线谱，用真实内核文档渲染同一小节的双谱，核对四分休止、品位、音高和吉他八度移调关系。
2. 验证点击拍位/弦、输入 3 和连续输入 12，候选即时可见且不需要确认，12 品只形成一个撤销步骤。
3. 修改、删除、撤销重做后两种谱面保持一致；重绘后焦点、编辑目标和 ID 映射保持正确。
4. 验证无效输入、缩放后点击以及持续按键，测量输入反馈与提交后双谱更新，不先声明达标。
5. 保存并重启重开，证明显示来自实际保存的音乐文档。通过后继续扩充 UI，而不是先实现完整排版引擎。
6. 分别启动“基础 UI + 通用记谱”和“基础 UI + 吉他领域/UI 贡献”两种配置，验证前者没有六线谱与品号入口、后者有适用的双谱与直接输入。按当前能力使用独立启动/新会话，不把此项描述为动态热加载验收。
7. 验证隐藏六线谱只改变视图、不会删除吉他数据；与缺少插件的处理明确区分，后者不能假定专属语义仍可正常编辑。
