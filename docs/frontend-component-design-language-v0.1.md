# 前端功能组件设计语言 v0.1

## 1. 文档目的

本文保存 Brilliant Guitar 工作台的功能组件设计规则。它定义组件怎样被理解、怎样进入工作台、何时存在、允许放在哪里，以及怎样在保持独特外观的同时维持一致的操作逻辑。

本文不冻结最终配色、装饰、精确尺寸或单个组件构图。视觉探索可以在独立样本中继续，但不能破坏这里定义的功能语义。

相关技术边界继续以 [前端模块化与 UI 插件边界](frontend-modularity-principles.md) 为准；操作频率和入口优先级继续以 [第一版操作频率地图](frontend-v1-operation-frequency-map.md) 为准。

## 2. 总体模型

一个完整功能组件由四部分组成：

> 组件 = 宿主能力 + 逻辑原型 + 领域内容 + 独特表达

- **宿主能力**：移动、停靠、缩放、隐藏、恢复、焦点、布局持久化和扩展装配。
- **逻辑原型**：用户理解组件和完成操作的基本顺序。
- **领域内容**：音符、播放、歌词、和弦、指板等实际业务。
- **独特表达**：构图、符号、空间、动画、声音反馈和视觉风格。

统一的重点是宿主能力与逻辑因果，不是让所有组件共享一个可见标题栏、矩形外框或按钮排布。

## 3. 三个分类轴

### 3.1 逻辑类型：组件怎样工作

| 逻辑类型 | 基本结构 | 代表组件 |
| --- | --- | --- |
| 工作区视图 | 内容、选择、直接操作、局部反馈 | 乐谱、结构视图、指板工作区 |
| 对象编辑器 | 当前对象、核心属性、修饰属性、结果反馈 | 音符、歌词、和弦、力度、奏法、指法 |
| 连续控制器 | 当前状态、主控制、连续参数、实时反馈 | 播放、缩放、节拍器、循环、录音 |
| 属性检查器 | 当前选择、属性分组、修改、验证 | 小节、谱表、音轨属性 |
| 状态导航器 | 当前节点、前后关系、跳转或恢复 | 历史记录、页面与段落导航 |
| 状态监视器 | 总体状态、事件详情、异常处理 | 播放输出、排版警告、插件状态 |
| 辅助工作流 | 当前上下文、建议、预览、接受或拒绝 | Agent、指法推荐、和弦助手 |
| 事务操作 | 操作目标、必要输入、验证、确认或取消 | 新建、导出、谱面设置、插件管理 |

### 3.2 生命周期：组件何时存在

| 生命周期 | 行为 | 示例 |
| --- | --- | --- |
| 应用级 | 始终存在，保证工作台可操作和可恢复 | 命令入口、组件库、布局恢复 |
| 文档级 | 打开谱子后存在，可移动、隐藏或关闭 | 播放、缩放、历史记录 |
| 工作模式级 | 进入某类工作后持续存在，不随每次选择反复开关 | 音符控制、歌词编辑、指法输入 |
| 用户保持级 | 用户打开后保留，直到主动关闭 | Agent、属性检查器、指板 |
| 上下文级 | 宿主保持稳定，内部内容随选择或状态变化 | 当前选择属性、当前音符信息 |
| 瞬时级 | 完成单次操作后消失 | 选择器、右键菜单、确认框 |

生命周期只描述存在时长，不决定组件是否固定在系统框架中。播放组件可以贯穿整个文档生命周期，但仍然由用户决定位置。

### 3.3 位置合同：组件可以去哪里

- 工作区视图只进入中央工作区或分屏区域。
- 对象编辑器可以进入上下左右停靠区，并按容器切换构图。
- 连续控制器可以进入四侧停靠区；横向与纵向需要分别设计。
- 检查器、监视器和辅助工作流优先进入侧边或底部，也可以声明完整工作区形态。
- 瞬时交互只进入对象附近浮层或对话框，不参与用户停靠布局。
- 扩展片段跟随所属组件，不自行占据工作台位置。

用户在组件声明的合法区域内决定实际位置。自由布局不是任意像素摆放；位置合同需要保护响应式行为、可访问性和整体视觉秩序。

## 4. 固定框架边界

固定框架只保留关闭全部工具后仍必须存在的能力：

- 当前文档身份和保存状态。
- 全局菜单或命令入口。
- 组件库入口。
- 布局保存、切换、恢复和重置入口。
- 全局通知、错误和后台任务状态。
- 操作系统窗口控制。

播放、缩放、历史记录、音符控制和属性检查器都不是固定框架的一部分。对应命令可以始终通过菜单或快捷键访问，但其可见组件由用户布置。

## 5. 通用功能语法

功能组件优先遵循以下认知顺序：

1. **作用对象**：当前操作的是输入草稿、已有音符、播放会话还是整个文档。
2. **当前状态**：对象现在是什么状态。
3. **核心动作**：最高频、最直接的改变方式。
4. **调整参数**：围绕核心动作组织的修饰和连续参数。
5. **结果反馈**：操作实际改变了什么，是否仍在处理或失败。
6. **次级能力**：低频设置、高级属性和插件扩展。
7. **恢复路径**：撤销、重试、重置或退出当前操作。

这七项是逻辑槽位，不是固定的七行布局。组件可以用音乐符号、轨迹、空间位置或动画来表达它们；只有必要信息需要持续可见。

## 6. 交互一致性

- 切换选择时优先更新组件内部对象和反馈，不反复展开、收起或移动整个组件。
- 高频操作直接作用并立即反馈，不要求额外确认；结果进入统一历史后可撤销。
- 中低频能力进入局部展开、对象附近浮层或事务界面，不永久占据主要空间。
- 动画表达因果、方向、层级和状态转移，不作为无意义的循环装饰。
- 外观独特不等于交互任意。相同逻辑原型应保留相似的作用对象识别、主次动作关系、反馈与恢复方式。

## 7. 宿主合同与视觉自由

工作台宿主统一提供：

- 停靠、移动、缩放、隐藏、恢复和布局持久化。
- 容器位置、实际尺寸、焦点和上下文。
- 组件菜单、权限校验、命令路由和扩展装配。
- 加载、不可用、错误和恢复状态的最低语义要求。

宿主合同不强制可见标题栏或相同外框。组件控制可以在布局编辑模式、悬停、聚焦或上下文菜单中出现。单个组件可以拥有自己的轮廓、内部节奏、图标、动画与空间隐喻。

组件至少提供与其合法位置对应的布局变体：

- `compact-horizontal`：顶部或底部紧凑形态。
- `compact-vertical`：左右窄栏形态。
- `panel`：标准工具面板形态。
- `workspace`：中央工作区完整形态，仅在业务需要时提供。
- `popover`：对象相关的瞬时形态。

布局变体应重新组织信息关系，不能只把同一排控件强行压缩或旋转。

## 8. 扩展规则

- 插件首先声明逻辑类型、生命周期、作用对象和合法位置，再声明视觉实现。
- 新能力优先进入已有组件的稳定扩展点，不为每项高级属性复制整个组件。
- 扩展内容继承所属组件的对象上下文、事务、历史、焦点和反馈通道。
- 特殊领域内容可以拥有独特构图，但不能绕过宿主命令和权限边界。
- 扩展不得改变组件核心动作的语义，也不得让基础功能依赖扩展存在。

建议的产品设计登记字段：

```text
名称
逻辑类型
作用对象
核心动作
调整参数
反馈方式
恢复路径
生命周期
合法位置
布局变体
扩展点
空状态、忙碌状态和错误状态
```

## 9. 当前组件登记

| 组件 | 逻辑类型 | 作用对象 | 生命周期 | 合法位置 |
| --- | --- | --- | --- | --- |
| 乐谱 | 工作区视图 | 完整谱面 | 文档级 | 中央、分屏 |
| 音符控制 | 对象编辑器 | 输入草稿或选中音符 | 工作模式级 | 四侧停靠 |
| 播放 | 连续控制器 | 当前谱面播放会话 | 文档级 | 四侧停靠 |
| 纸张缩放 | 连续控制器 | 乐谱观察尺度 | 文档级 | 四侧紧凑区域 |
| 历史记录 | 状态导航器 | 文档操作历史 | 文档级 | 四侧停靠 |
| 播放输出 | 状态监视器 | 播放状态与输出信息 | 用户保持级 | 侧边、底部 |
| Agent | 辅助工作流 | 当前谱面与选择上下文 | 用户保持级 | 侧边、底部、工作区 |

## 10. 首个验证样本：音符控制

音符控制用于验证对象编辑器原型、工作模式生命周期、多位置布局和扩展装配。第一轮完整样本至少覆盖：

- 明确区分“下一次输入”与“当前选中音符”。
- 音高、组号、变音、时值、附点和音符／休止符切换。
- 小节占比、谱面位置、提交中、不可用和失败反馈。
- 高频修改无需展开或确认，且操作结果可进入统一撤销历史。
- 组件保持稳定，选区变化只更新内部对象和状态。
- 音符符号与状态变化形成可感知但不干扰输入的运动反馈。
- 为力度、奏法、技巧、弦品和特定谱式内容保留稳定扩展位置。
- 至少验证一个纵向停靠形态和一个横向停靠形态。

该样本通过后，再把已经验证的规则扩展到播放组件，以检验连续控制器能否在同一工作台系统中保持独特表达。

## 11. 后续规划：组件视觉效果设置

记录日期：2026-09-20。状态：已记录需求，留待后续会话设计与实现；当前审美样本不代表效果已默认启用或正式接入。

- 各功能组件提供逻辑一致的视觉效果设置入口，让用户自行取舍视觉表现与运行性能；入口不必常驻占据组件的主要操作空间。
- 对组件实际具有的复杂效果提供独立开关，例如柔光、背景模糊、透明叠层和装饰性动画，不为不存在的效果展示无效选项。
- 关闭效果后，选中、焦点、启用、禁用、处理进度等必要状态仍须清晰可辨，组件功能、布局与输入响应保持可用。
- 关闭效果必须停止对应的动画、持续更新或额外渲染工作，不能仅把效果设为透明；实现时以实际性能测量验证收益。
- 效果设置与系统“减少动态效果”偏好的关系需要统一设计，不能通过组件设置绕过减少动态效果的约束。
- 插件扩展的复杂效果也应遵循同一设置逻辑，同时允许组件保留独特的视觉表达。

后续待定：默认启用项、开关粒度、设置入口、偏好的持久化范围，以及是否需要全局性能预设和组件级覆盖。以上问题尚未定案，不在当前光效与配色实验中实现。
