# Pure Core Kernel V1 小功能索引

## 目的

本目录用于把 Pure Core Kernel V1 的 9 类内核机制拆成小功能。每个小功能都必须可审核、可实现、可测试、可追踪，避免后续 AI 从“实现文档模型”这种大词直接自由发挥。

后续代码实现时，不应该只引用“实现 K1”，而应该明确引用 `K1-F004`、`K1-F007` 这类小功能 ID。

## 追踪契约

- 每个内核小功能使用 `K<机制编号>-F<序号>`，例如 `K1-F001`。
- 每个小功能文档必须包含四类视角: 产品视角、业务逻辑视角、技术实现视角、反过度设计视角。
- 每次实现提交必须说明实现了哪些小功能 ID。
- 每个测试文件或测试用例应该在名称、描述或相邻注释中引用对应小功能 ID。
- 如果代码行为与小功能文档冲突，先停下来更新文档并让用户审核，不允许在代码里自行重新解释需求。
- 新增内核概念必须映射到 9 类机制之一；如果映射不清楚，必须先做单独边界审查，不能直接写进内核。

## 小功能模板

每个小功能使用以下结构:

```markdown
### Kx-Fyyy: 功能名

产品视角:
- 解决什么用户问题。
- MVP 使用场景是什么。

业务逻辑视角:
- 状态如何变化。
- 合法/非法规则是什么。
- 错误或 unsupported 行为是什么。

技术实现视角:
- 涉及哪些数据模型、API、schema、validator、event、registry 或 diagnostic 契约。
- 依赖哪些需求或 spec。
- 必须覆盖哪些测试。

反过度设计视角:
- V1 明确不实现什么。
- 哪些扩展点只预留，不激活。

验收标准:
- ...

测试要求:
- ...
```

## 编码前一致性门禁

实现任意小功能前，必须满足:

- 小功能 ID 已存在于本目录。
- 该 ID 有且只有一个主内核机制归属。
- 跨机制依赖已经显式列出。
- `.trellis/spec/core-kernel/backend/` 中对应稳定 spec 与小功能契约一致。
- `implement.md` 中的实现清单不与小功能文档冲突。
- 如果小功能有验证行为，测试计划至少包含一个正常用例和一个失败或 unsupported 用例。
