# REQ-016 长期维护、版本演进和兼容策略

## 决策状态

- 状态: 已确认项目原则
- 合并目标: 最终 PRD 的长期维护、版本兼容、发布治理和演进策略
- 用户决策: 长期维护是项目原则，必须从始至终一直保持执行。本项目作为毕业设计，但不是随便做的软件。

## 用户价值

打谱软件保存的是用户长期创作资产。用户需要相信今天创建的 `.bgp` 文件，在后续版本中仍然能打开、迁移、导出和继续编辑。开发者也需要一个稳定的演进规则，避免为了短期演示写出难以维护的架构。

## 维护定位

- 毕业设计版本是第一个产品里程碑，不是一次性 demo。
- 第一阶段可以控制功能范围，但不能牺牲架构边界、文件兼容、测试回归和发布纪律。
- 长期维护优先保护用户作品，其次保护开发效率，再考虑扩展生态。
- 长期维护原则不得被短期演示、毕业设计进度、MVP 取舍或单个功能需求覆盖。

## MVP 必须满足

- REQ-016-F01: 项目从第一阶段开始使用明确版本号，建议采用 SemVer。
- REQ-016-F02: `.bgp` 文件必须包含格式标识、schema version、创建应用版本和最后保存应用版本。
- REQ-016-F03: 每个稳定 schema version 必须至少有一个 fixture 文件用于回归测试。
- REQ-016-F04: 打开旧版本 `.bgp` 文件时必须经过迁移器或兼容读取路径，不得静默丢数据。
- REQ-016-F05: 打开未来版本 `.bgp` 文件时必须安全失败，并提示当前应用不支持该文件版本。
- REQ-016-F06: 领域模型、命令系统、文件格式、渲染、播放和插件边界不得为了演示临时绕开。
- REQ-016-F07: 重要架构决策必须写入设计文档或 ADR。
- REQ-016-F08: 每次发布必须包含变更日志、已知问题和兼容性说明。
- REQ-016-F09: `Guitar Core Loop` 必须作为长期回归场景保留。
- REQ-016-F10: 1.x 稳定版必须能打开所有 1.x 稳定版保存的 `.bgp` 文件；无法兼容时必须升级主版本并提供迁移说明。
- REQ-016-F11: 长期维护规则必须进入 `.trellis/spec`，作为后续编码任务的项目级约束。

## 行为契约

- 文件兼容问题优先级高于新增功能。
- 维护原则从项目启动到后续开源维护阶段一直有效，不因毕设进度、MVP 取舍或未来路线变化而失效。
- 任何 schema 字段删除、重命名、语义改变都必须有迁移策略。
- 任何新增技巧、乐器、轨道类型或导出格式都必须说明对旧文件的影响。
- 自动保存文件和正式保存文件必须区分版本和来源。
- 开源贡献不得绕过兼容性测试、类型检查、文件 round-trip 测试和许可证检查。

## 第一阶段不做

- 不承诺长期支持所有实验性 nightly 文件。
- 不承诺兼容尚未实现的 Guitar Pro 文件格式。
- 不承诺云端同步兼容策略。
- 不承诺第三方插件 API 稳定。
- 不做企业级 LTS 服务承诺。

## 验收标准

- [ ] AC-016-01: `.bgp` 文件中能看到明确的 schema version 和应用版本字段。
- [ ] AC-016-02: 至少一个 `Guitar Core Loop` fixture 能完成保存、打开、校验和导出回归。
- [ ] AC-016-03: 应用遇到未来 schema version 文件时不会崩溃，并给出可读错误。
- [ ] AC-016-04: 实现计划中包含版本号、变更日志、兼容性测试和发布说明。
- [ ] AC-016-05: 代码结构能说明哪些模块属于稳定核心，哪些模块属于实验性扩展。
- [ ] AC-016-06: 毕设材料中能说明项目的长期维护路线，而不是只展示一次性演示。
- [ ] AC-016-07: `.trellis/spec` 中存在项目级长期维护 guide，后续实现任务必须遵守。
- [ ] AC-016-08: 1.x 兼容承诺能映射到文件 fixture、迁移测试和发布检查清单。

## 开放问题

- 无。长期维护已确认为项目原则，且 1.x 稳定版 `.bgp` 兼容承诺从第一阶段开始执行。
