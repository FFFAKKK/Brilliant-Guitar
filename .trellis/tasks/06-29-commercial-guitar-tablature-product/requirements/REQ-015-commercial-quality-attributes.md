# REQ-015 商业级质量属性、质量门禁和工程验收

## 决策状态

- 状态: 已收敛；Windows 质量基准已确认，具体运行指标后续阶段细化，不阻塞 Pure Core Kernel V1
- 合并目标: 最终 PRD 的非功能需求、质量属性和发布准入标准
- 已确认决策: 项目先开源验证效果，但必须按商业软件流程建设
- 已确认决策: 第一阶段质量基准平台为 Windows 桌面
- 已确认决策: 长期维护是项目原则，必须从始至终一直执行；毕业设计版本必须作为长期维护产品的第一个稳定基础，而不是一次性演示工程

## 用户价值

打谱软件承载的是用户作品。即使第一阶段开源验证，也不能只是一个能演示的玩具项目。用户需要相信它不会轻易丢谱、损坏文件、卡死、泄露谱面、错误导出或在后续版本中无法打开旧文件。

## 质量属性总览

第一阶段必须覆盖以下质量属性:

- 健壮性: 面对非法输入、损坏文件、异常命令、导出失败和恢复流程时不崩溃、不丢数据。
- 安全性: 外部文件、导入内容、插件、资源包、诊断包和日志按不可信输入处理。
- 高效性: 常用编辑、播放光标、保存打开和导出有明确响应预期。
- 可靠性: 保存、自动保存、崩溃恢复和版本迁移保护用户作品。
- 可维护性: 模块边界清晰，领域模型不被 UI、播放、渲染和文件格式污染。
- 可测试性: 核心能力可用自动化测试、fixture、golden file 和命令回放验证。
- 可发布性: 发布包有版本、许可、诊断、更新日志和发布检查清单。
- 可扩展性: 插件和后置能力通过明确扩展点进入，不能破坏核心模型。
- 可演进性: 文件格式、领域模型、命令系统和插件边界必须支持长期版本演进、迁移和废弃策略。

## MVP 必须满足

- REQ-015-F01: 每个核心功能必须有可测试验收标准，不得只写“支持某功能”。
- REQ-015-F02: 所有编辑命令必须可验证、可撤销、可回放。
- REQ-015-F03: 打开文件必须先经过格式、schema version 和文档验证。
- REQ-015-F04: 保存失败不得破坏原文件；自动保存不得覆盖用户正式保存文件。
- REQ-015-F05: 导入必须输出 `ImportReport`，导出必须输出 `ExportReport`。
- REQ-015-F06: 所有用户可见错误必须有可读原因和下一步建议。
- REQ-015-F07: 崩溃日志和诊断包默认不得包含用户谱面正文，除非用户明确选择。
- REQ-015-F08: 插件、导入文件、资源文件和外部谱面必须按不可信输入处理。
- REQ-015-F09: 核心模块必须能在无 UI 环境下运行单元测试或集成测试。
- REQ-015-F10: 发布前必须通过质量门禁，失败项不得以“后续修复”绕过。
- REQ-015-F11: 任何破坏旧文件、旧 fixture 或旧命令回放的变更都必须有迁移方案、兼容说明和测试证明。
- REQ-015-F12: 版本发布必须包含版本号、变更日志、已知问题、迁移说明和回滚建议。
- REQ-015-F13: 任何功能实现不得以“只是 MVP”或“只是毕设”为理由绕过长期维护、文件兼容和回归测试要求。

## 健壮性要求

- Core Kernel K1 必须发现非法 `AbsolutePitch`、调弦、时值、小节结构、slot/event 引用和技巧组合；非法弦号/品号属于后续吉他谱模块验证，不属于 Pure Core Kernel V1 硬验证。
- 损坏原生文件必须给出可读错误，不得导致应用崩溃。
- 文件版本过新时必须阻止错误打开，并说明当前软件不支持该版本。
- 导出失败必须保留原谱面状态，不得污染当前文档。
- 撤销/重做在连续多步操作后必须保持文档一致。

## 安全与隐私要求

- 默认离线可用，核心编辑能力不依赖登录。
- 用户谱面不得默认上传。
- 插件权限必须显式声明，第三方插件安装后置。
- 导入器不得执行外部文件中包含的脚本、命令或任意路径引用。
- 诊断包必须区分系统信息、日志、崩溃栈和用户作品内容。
- 第三方依赖、字体、图标、音色和示例谱必须有许可证记录。

## 性能与效率要求

第一阶段以 Windows 桌面为质量基准平台，先使用体验级阈值，具体数值在技术设计阶段细化:

- 常见输入、选择、撤销、重做应接近即时反馈。
- 打开、保存和导出中大型谱面时 UI 不得假死。
- 播放光标必须稳定跟随，不能明显跳动或卡顿。
- PDF/PNG 导出必须有忙碌状态、成功结果或失败原因。
- 性能测试必须至少覆盖打开、保存、编辑命令、播放光标和导出。

## 可维护性要求

- UI 不得直接修改谱面文档对象。
- 文件格式、领域模型、命令系统、渲染、播放和插件必须保持边界。
- 数据模型修改必须同时更新 schema、迁移、验证器和 fixture。
- 新增技巧必须同时更新技巧枚举、显示语义、播放语义、验证规则和测试谱库。
- 新增导入导出格式必须声明兼容范围和降级规则。
- 禁止为了短期演示绕过领域模型、命令系统、schema 或验证器。
- 重要架构决策必须写入设计文档或 ADR，避免后续维护时只能从代码猜意图。

## 测试要求

- 领域模型单元测试。
- 命令系统 undo/redo 测试。
- 文件打开、保存、迁移和损坏文件测试。
- P0 吉他技巧 fixture 测试。
- 导出 PDF/PNG 的可读性或快照测试。
- 播放事件生成测试。
- 国际化 key 完整性测试。
- 基础安全检查和依赖许可检查。

## 发布门禁

发布前必须确认:

- 类型检查通过。
- lint 或格式检查通过。
- 核心单元测试通过。
- 文件格式 fixture 回归通过。
- 导入导出回归通过。
- 安全与隐私检查通过。
- 第三方许可清单更新。
- 版本号、更新日志和已知问题清单更新。
- Windows 安装、启动、文件关联、保存、打开、自动保存恢复、PDF/PNG 导出和诊断包导出演示通过。

## MVP 不做

- 不做企业级合规认证。
- 不做安全审计报告作为第一阶段发布条件。
- 不做复杂遥测平台。
- 不做云端 SLA。
- 不做第三方插件沙箱的完整产品化开放。

## 验收标准

- [ ] AC-015-01: 每个第一阶段核心功能至少有一个自动化测试或明确人工验收步骤。
- [ ] AC-015-02: 保存失败、损坏文件、非法谱面和导出失败都有可读错误。
- [ ] AC-015-03: 诊断包默认不包含用户谱面正文。
- [ ] AC-015-04: 质量门禁清单能在实现计划中逐项映射到命令、测试或人工检查。
- [ ] AC-015-05: 性能基准至少覆盖打开、保存、编辑命令、播放光标和 PDF/PNG 导出。
