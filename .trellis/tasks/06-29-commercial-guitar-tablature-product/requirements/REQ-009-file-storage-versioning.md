# REQ-009 本地文件、自动保存、版本与迁移

## 决策状态

- 状态: 文件策略、扩展名、产品名和第一阶段不加密已确认
- 合并目标: 最终 PRD 的存储和可靠性要求
- 关键开放问题: 无。第一阶段不支持文件密码锁、加密保存或 DRM。

## 用户价值

用户的谱面是作品和商业资产。文件必须可备份、可迁移、可恢复，并且不能因为软件升级或崩溃轻易损坏。

## 推荐原生格式

MVP 已确认采用“GP8 式单文件体验 + 开放包结构”:

- 文件扩展名为 `.bgp`，含义为 `Brilliant Guitar Project`。
- 产品名暂定 `Brilliant Guitar`。
- 物理形态为 zip 包。
- 包内包含 `manifest.json`、核心谱面数据、资源目录和插件私有数据目录。
- 核心谱面数据使用可读结构化格式，例如 JSON。

原因:

- 单文件方便分享。
- zip 包可容纳音频、图片、缩略图和未来资源。
- JSON 方便调试、迁移和 AI 生成。
- manifest 可承载版本、依赖、资源索引和完整性校验。
- 项目先开源验证效果，开放包结构能让社区更容易提交问题、制作测试文件、验证迁移和开发生态工具。

更多对比见 `../research/native-file-format-comparison.md`。

## MVP 必须满足

- REQ-009-F01: 支持新建、打开、保存、另存为。
- REQ-009-F02: 支持自动保存。
- REQ-009-F03: 支持崩溃恢复草稿。
- REQ-009-F04: 支持最近文件列表。
- REQ-009-F05: 支持 schema version。
- REQ-009-F06: 支持文件打开时迁移旧版本。
- REQ-009-F07: 支持保存前文档验证。
- REQ-009-F08: 支持未知插件数据保留。
- REQ-009-F09: 原生文件包结构必须形成公开 spec，至少说明包目录、manifest、score 数据、资源引用、schema version 和兼容策略。
- REQ-009-F10: 第一阶段不得把核心谱面语义存入不可审查的私有二进制黑盒；后续可增加缓存、签名或商业保护层，但不得替代核心语义来源。
- REQ-009-F11: 第一阶段 `.bgp` 不得启用文件密码锁、加密保存或 DRM；核心 `manifest.json`、`score.json`、schema version 和迁移信息必须可被测试工具解包检查。

## 数据完整性

- 保存必须尽量使用原子写入策略，避免半写入损坏原文件。
- 自动保存文件必须与用户正式保存文件区分。
- 文件损坏时必须给出可读错误，而不是直接崩溃。
- 迁移必须保留原文件备份或让用户确认。
- 打开新版本文件时，如果当前软件不支持，必须给出明确提示。

## MVP 不做

- 不做多人实时协作合并。
- 不做云端版本历史。
- 不做文件密码锁。
- 不做加密保存。
- 不做版权 DRM 文件锁作为基础存储机制。
- 不做私有黑盒原生文件格式作为第一阶段基础。

## 验收标准

- [ ] AC-009-01: 用户保存后重新打开，谱面、轨道、调弦、技巧、布局和元数据一致。
- [ ] AC-009-02: 模拟崩溃后，用户下次打开能恢复自动保存草稿。
- [ ] AC-009-03: 打开 schema 旧版本文件时，系统执行迁移并记录迁移结果。
- [ ] AC-009-04: 保存过程中失败时，原文件不被破坏。
- [ ] AC-009-05: 将原生文件包解压后，开发者能根据公开 spec 识别 `manifest`、核心谱面数据、资源目录和扩展数据目录。
- [ ] AC-009-06: 第一阶段保存的 `.bgp` 文件可由测试工具解包检查 `manifest.json` 和 `score.json`，不要求输入密码或授权。

## 开放问题

- 无。第一阶段不支持文件密码锁、加密保存或 DRM；后续如需商业保护层必须单独设计且不得替代开放核心语义。
