# SPEC-000 文档与规格契约

## 状态

- 状态: 草案
- 作用: 约束后续所有 PRD、需求、架构、spec、设计和实现计划的写法。
- 目标: 让后续 AI 写代码时输入清晰、边界明确、结果可验收。

## 强制规则

- DOC-001: 每个需求必须有稳定编号，例如 `REQ-003`。
- DOC-002: 每个规格必须有稳定编号，例如 `SPEC-004`。
- DOC-003: 文档不得只写愿景，必须包含可验收行为。
- DOC-004: 每个 MVP 功能必须明确“必须做”“后置做”“明确不做”。
- DOC-005: 每个开放问题必须有推荐答案和取舍说明。
- DOC-006: 用户确认后的答案必须写回对应文档。
- DOC-007: 已解决问题不得长期留在开放问题区。
- DOC-008: 技术方案必须写清模块边界和依赖方向。
- DOC-009: spec 必须能指导测试，不可只写抽象原则。
- DOC-010: 最终合并 PRD 前必须做一次收敛，删除重复和过期草案。
- DOC-011: 每个功能、模块或内核子系统规划必须包含“产品视角、业务逻辑视角、技术实现视角、反过度设计视角”四类说明。
- DOC-012: 反过度设计视角必须明确当前阶段保留、后置和拒绝的复杂度，不得只写“避免过度设计”。

## 禁止事项

- 不允许让实现者自行选择核心技术栈。
- 不允许在 React 组件中临时发明谱面数据结构。
- 不允许把“像 Guitar Pro 一样”作为可执行需求。
- 不允许把不可验证的描述当作验收标准。
- 不允许同一个业务规则散落在多个文档且表述不同。
- 不允许新增功能规划时只写技术结构，不解释用户问题、业务流程和 MVP 简化理由。

## 文档模板要求

每个 `REQ` 文档至少包含:

- 用户价值。
- 当前决策状态。
- 规划审核视角。
- MVP 必须满足。
- MVP 不做。
- 行为契约。
- 验收标准。
- 开放问题。

每个 `SPEC` 文档至少包含:

- 目标。
- 适用范围。
- 强制规则。
- 数据或接口契约。
- 错误和边界行为。
- 测试要求。
- 与需求编号的映射。

## 验收标准

- [ ] AC-SPEC-000-01: 新增需求文档时能找到 `REQ` 编号、行为契约和验收标准。
- [ ] AC-SPEC-000-02: 新增 spec 文档时能找到强制规则、接口契约和测试要求。
- [ ] AC-SPEC-000-03: 任意实现任务开始前，关联需求和 spec 都没有未标记的关键开放问题。
- [ ] AC-SPEC-000-04: 文档中出现默认假设时，必须标记为“默认”或“未确认”。
- [ ] AC-SPEC-000-05: 新增或继续规划功能时，文档中能找到产品视角、业务逻辑视角、技术实现视角和反过度设计视角。
