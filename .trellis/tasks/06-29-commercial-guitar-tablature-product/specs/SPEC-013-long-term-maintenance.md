# SPEC-013 长期维护原则

## 状态

- 状态: 已确认项目级原则
- 映射需求: `REQ-016`
- 目标: 约束后续所有实现任务，确保毕业设计版本是长期产品的第一个可维护版本。

## 强制规则

- 长期维护是项目原则，必须从始至终一直执行。
- 任何功能不得以“只是 MVP”“只是毕设”“只是演示”为理由绕过领域模型、命令系统、schema、迁移、验证器或回归测试。
- `.bgp` 必须包含格式标识、schema version、创建应用版本和最后保存应用版本。
- 1.x 稳定版必须能打开所有 1.x 稳定版保存的 `.bgp` 文件。
- 每个稳定 schema version 必须至少有一个 fixture 文件。
- schema 字段删除、重命名或语义改变必须提供迁移策略和兼容性测试。
- 重要架构决策必须写入设计文档或 ADR。
- 每次发布必须包含版本号、变更日志、已知问题、兼容性说明和迁移说明。

## 禁止事项

- 禁止在 UI 组件中写死谱面语义以绕过领域模型。
- 禁止为了演示直接写 `.bgp` JSON 而绕过文件服务和验证器。
- 禁止静默丢弃旧文件中的未知字段、插件私有数据或未来可恢复信息。
- 禁止没有迁移说明就破坏旧 fixture、旧命令回放或旧文件 round-trip。

## 测试要求

- `Guitar Core Loop` 必须作为长期回归场景保留。
- 文件 round-trip 测试必须覆盖当前 schema fixture。
- 未来 schema version 文件必须安全失败并给出可读错误。
- 迁移器必须覆盖至少一个旧版本到当前版本的测试场景，一旦存在旧稳定 schema。

## 发布要求

- 发布前必须检查 schema version、fixture、迁移器、变更日志和兼容性说明。
- 破坏兼容性的变更必须升级主版本，并在发布说明中明确说明影响。
- 任何实验性能力必须标明实验状态，不能默认获得稳定兼容承诺。
