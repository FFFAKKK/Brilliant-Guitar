# 插件反馈与可替换呈现：扩展边界提案

日期：2026-10-04。状态：目标契约，未实现；本文件不是当前SDK字段或新增API。

## 1. 目标和责任

用户要求规划考虑后续插件增加，避免功能插件直接耦合具体错误处理、通知实现或界面，导致每次扩展都要重构。接口边界、兼容和替换验收从现在设计，默认实现暂由包内模块提供也必须依赖这些边界。

扩展目标是：使用已发布合同新增一个插件，或在下一次固定会话选择另一种反馈呈现实现，既有功能插件和业务处理无需修改。新增能力超出合同则按版本机制扩展，不能承诺任意未来能力都无需调整宿主。

业务失败的判断、事务和恢复条件仍属于业务状态所有者；UI承载、授权、焦点和生命周期属于宿主；反馈记录与呈现通过受限合同协作。反馈记录描述操作已报告的状态，不成为第二份乐谱、事务或业务错误真值。

对应设计原则见[插件设计主稿](./plugin-design-v0.1.md)第7、11节；视觉表达见[第六批方向](../../.trellis/tasks/10-01-backup-frame-visual-polish/research/quiet-feedback-direction-20261004.md)。

跨层责任、现有桌面结果与前期影响见[错误反馈跨层审查](./feedback-cross-layer-review.md)。UI自身故障通常交宿主诊断，内核业务结果由应用服务返回，其他插件问题在所属执行边界处理；错误报告不作为谱面事务提交给Core。该审查尚无真实IPC或业务验收。

## 2. 两处接口边界

```text
功能插件及其获准的领域入口
  → 来源绑定的反馈报告端口
  → 单一反馈记录与只读投影
  → 可替换的反馈呈现实现

用户选择恢复动作
  → 宿主检查当前权限、作用目标与可用性
  → 原有命令或类型化领域入口
  → 状态所有者返回真实结果并更新反馈
```

报告方依赖报告合同，呈现方依赖投影合同。两者不导入对方实现，不接收完整消息仓库、router、store或他人DOM，不按具体插件名称或已知错误码写宿主特判。

此接口仅描述反馈及恢复入口，不增加全局业务Gateway、任意事件总线、第二个命令路由器或第二套插件平台。默认实现与以后独立登记的实现都应消费相同的接口。

## 3. 是否独立登记为插件

为反馈报告、记录与呈现分别确定公开合同和可替换实现。独立部署、装配或替换成为实际产品需求时，对应实现可以作为平级插件登记；一个实现可以组合多项可选贡献，不新增“错误／通知／进度插件”等强制类型。

默认提供者即使由组合根直接装配，也不能借此绕过报告与消费接口。独立登记后使用同一平台身份、兼容要求、固定启动集合、权限和生命周期，服务接入通过既有可信宿主授权机制提供，不让消费者绑定提供者命名空间。必需能力版本、提供者选择及冲突必须在启动计划中明确；不按加载顺序覆盖。

全局主要呈现选择一个有效提供者，避免每个提供者都播报同一问题；局部组件可以保留自有视觉，但通过同一问题身份关联记录。辅助读取只按合同获准的范围工作，不隐式取得全部反馈或业务执行能力。运行中热替换不加入当前范围。

## 4. 工程定版前必须明确的语义

下表是候选接口内部语义要求，正式键名、签名和协议版本仍待工程定版。它们不增加所有插件共同最小声明的必填项，也不要求所有插件报告进度、产生通知或提供恢复动作。

| 语义 | 目标约束 |
| --- | --- |
| 协议兼容 | 报告与投影合同分别明确版本与兼容；已支持能力可查询，不从具体实现名称推断 |
| 来源 | 宿主绑定实际插件／组件实例和会话身份，作者不能冒领他人来源 |
| 操作关联 | 同一操作的按钮、菜单、快捷键反馈可关联；两个插件相同的局部编号不合并；重试与新尝试的关系明确 |
| 记录身份与更新 | 宿主签发所属记录的受限更新句柄，校验会话、所有者及更新次序；重复、过期及释放后的更新有明确拒绝 |
| 结果或问题 | 有可读摘要和必要的稳定诊断码；新错误码可以默认显示摘要，未认识的扩展信息不导致空白或假成功 |
| 真实操作结局 | 保留已确认提交、无变化、拒绝、部分完成及待核对的区别，沿用原合同中的警告／unsupported；传输失败不能自行推断未提交 |
| 目标和影响 | 目标来自允许的字段／组件／工作区引用，缺失或隐藏目标有可达回退；不接受任意CSS选择器或DOM写权限 |
| 生命周期 | 进行中、完成、失败、取消、关闭、已查看、已解决的含义分别说明；关闭展示不代表问题已解决或业务已撤回 |
| 恢复入口 | 可省略；存在时引用已有获准动作及参数，说明真正重试／撤销／取消能力；不向呈现方传任意执行闭包或完整业务对象 |
| 更新和容量 | 同任务的更新、聚合、记录数量和保留策略有可执行合同；普通历史淘汰不能静默抹去尚待处理的问题 |
| 只读消费 | 可替换呈现取得相同稳定投影与订阅；原位／跨区域状态都从投影消费，处理结果仍由对应所有者决定 |
| 私有详情 | 可选且有明确结构、大小与读取许可；公开摘要不依赖每个消费者理解插件私有信息 |
| 宿主诊断 | 诊断与当前反馈分别承担留存和呈现，可按许可关联编号；日志失败不删除反馈或改变业务结局，旧诊断白名单不等于新反馈错误码集合 |
| 无贡献与错误 | 可选动作／详情／呈现贡献缺失按合同为空；必需端口缺失、无效报告与报告失败保持明确诊断，不吞成成功 |

修改反馈状态只属于该报告的所有者；展示实现可以请求隐藏视图或标记已查看，不能直接宣布业务问题解决。业务操作结果与反馈报告成功是两件事：记录失败不能触发第二次业务执行，也不能把业务失败改为成功。

恢复动作在用户选择时重新检查当前作用目标、版本和权限；去重、防重复、取消和幂等由原执行合同处理。呈现插件不直接决定可以重试，不绕过原动作执行链。

UI故障若需要释放资源、暂停订阅或结束业务会话，调用已有获准生命周期端口；上报问题本身不等于已取消业务。提交后传输或投影读取失败时先按原执行合同核对结局；没有可靠查询就保留待核对，不能只凭文档版本变化宣布成功或自动重发。报告、日志和订阅者失败不能覆盖已经确认的事务结果。

## 5. 默认提供、故障和替换

正常宿主提供版本明确的基础反馈能力。必需报告端口不可用时按启动／调用合同显式处理，不以空函数伪装已记录。可选装饰或额外详情没有提供者时保留基础表现，合法无贡献插件继续可登记。

宿主保留小范围的基础可见反馈路径，在所选呈现实现失败时仍能显示未解决的重要摘要。此路径不依赖已失败的呈现实现，不反复报告自身故障，不承担业务修复。具体位置沿用框架已有状态位置，避免自动新增模态或推动谱页。

替换呈现不改变业务结果、记录身份和已报告状态。替换反馈记录实现需要明确状态交接、保留规则和错误策略；没有迁移合同不能假定替换后能保留旧记录。选择新的提供者在下一固定会话生效，依旧由同一平台装配与释放。

可替换不等于安全或进程隔离；同主线程实现也不能承诺任意同步代码都能被强制中断。资源与更新预算按实际可执行能力验收。

## 6. 当前实现与迁移

当前createNotices保存文本、级别、来源及时间，最多保存50条历史；ctx.notify由组件宿主绑定来源。现有命令直接返回handler结果或Promise，异常可能向调用方传播，旧同步空返回按既有规则视为成功。当前没有本提案的操作更新句柄、解决状态、恢复引用或可替换提供者接口。

迁移集中在现有组合根及边界适配处：

1. 保留旧notify／confirm和命令的公开语义，增加已发布合同的适配层；已有调用者不直接改为依赖新呈现实现。
2. 旧文本通知可规范化为基础记录；没有操作身份时单独记录，不能靠相同文字猜测同一失败。缺乏细节时不能伪造可重试、可撤销或已解决。
3. 异常与命令结果按已知动作合同在其真实执行边界转换；同步和异步分别处理，不把任意返回值或所有异常强行套成业务失败。按钮、菜单与键位避免重复生成同一执行报告。
4. 报告与呈现合同采用版本规则；新增可选信息在兼容范围内默认表达，破坏性字段或语义变化发布新版本与适配。规范明确未知字段、错误码及旧记录处理。
5. 既有菜单和确认中的局部说明与历史记录逐步关联；不先删局部反馈，也不因改视觉而擅自移除确认的执行与焦点合同。
6. 当前50条历史机制不满足重要未解决问题的保留要求；工程需定义容量策略，不能直接把旧仓库当作完成版。
7. 在原类型化业务边界集中适配HostError、内核结果与能力返回分支；旧issue缺省仍按失败处理，未知码有基础说明，内层拒绝不因IPC成功而变为成功。平台原Error仅留内部诊断，反馈订阅与记录故障单独隔离；详见跨层审查的现状与矩阵。

尚无正式反馈声明、服务或呈现根字段；作者不能将本提案内容传入当前defineUiPlugin，也不能借假面板取得无界面插件生命周期。新端口需达到设计主稿第11节的合同与消费门槛。

## 7. 扩展性验收

本阶段先把下列场景写入工程交接，再通过实际端口装配验证；当前没有实施或运行这些用例。

| 场景 | 应证明的结果 |
| --- | --- |
| 新增插件A／B | 都只依赖已发布报告接口，宿主和其他插件没有新增名称分支或私有导入 |
| A／B使用相同局部任务编号 | 所有权隔离，互不覆盖、解决或读取未经许可的详情 |
| 按钮／菜单／键位执行同一动作 | 按实际执行身份关联，真实一次执行只有一次主要报告 |
| 新增未知错误码 | 仍能显示摘要及有效动作，不需要改宿主错误码枚举才能接入 |
| 换另一呈现提供者 | 既有功能插件和报告不变；状态一致，重要问题可达，谱页不移动 |
| 提供者缺失、冲突或版本不兼容 | 必需能力明确拒绝或采用已声明默认策略，不静默失效或加载顺序覆盖 |
| 呈现实现启动／运行失败 | 宿主最小可见回退有效，清理完整，失败报告没有递归 |
| 旧notify／confirm调用 | 兼容策略明确，已有结果和执行次数不变，不伪造新恢复能力 |
| 隐藏、释放及旧请求完成 | 重要问题按策略可达；失效上下文不能更新新会话或执行旧恢复动作 |
| 同任务更新及新尝试 | 次序明确，旧完成不覆盖新状态；重试结果引用对应真实执行 |
| 恢复动作权限或目标改变 | 执行时再次拒绝或更新可用性，不直接调用已失效闭包 |
| 记录容量到达上限 | 超限策略可见，未解决的重要问题不无声消失 |
| UI／内核／其他插件的失败 | 真实来源和原执行结局保持，UI故障记录不增加Core事务；未知码不要求修改已有功能插件 |
| 提交后传输／投影／日志故障 | 不把未知结局当拒绝，不重发已确认写入；反馈设施失败不改变业务结果或执行次数 |

工程依赖应在代表性业务插件扩大制作前确定：先发布与验证报告／消费合同、集中适配旧接口、再新增独立插件和默认提供者。视觉会话只提供原位与宿主承载状态及验证要求，正式协议和具体插件由工程会话落地。
