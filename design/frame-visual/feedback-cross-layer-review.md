# 错误反馈跨层审查与视觉交接

日期：2026-10-04。状态：源码审查、设计要求与工程交接；未实现反馈SDK、桌面接线或业务插件。本文件补充[反馈扩展边界](./feedback-extension-boundary.md)，不发布新的接口字段。

## 1. 范围、结论与证据层次

用户要求继续完善反馈设计，检查前期成果是否受影响，并考虑UI错误、内核错误与其他插件错误之间的协作。

需要结合内核已有结果合同设计，但UI错误通常交给UI宿主或桌面诊断服务，不作为乐谱命令提交给纯内核。内核拥有事务结果，应用服务拥有业务与宿主边界转换，UI拥有呈现与交互；其他插件的问题按实际执行边界处理。以下按责任描述错误流向，不为插件增加功能分类。

本轮检查的是仓库源码和规范，没有启动桌面、调用真实IPC或触发内核事务。备份框架的谱面仍是静态只读图，不能声称已打通双向反馈。没有读取、参考或修改废案产品UI；桌面应用服务和Rust合同只用于确认功能边界，不作为视觉来源。

纯Core规范中仍保留RKP-0阶段的TS权威记录；桌面Cargo和应用服务源码已引用Rust会话。两者的作用域和阶段需要分别核对，不能根据旧规范推断桌面运行TS，也不能根据桌面依赖宣布所有Core线路已切换。本会话不修改内核治理或运行权威。

### 备份UI当前机制

现有`ctx.notify(text, level)`绑定组件来源；`router.execute(id, payload)`可能直接返回结果、Promise或抛异常，旧同步空返回仍兼容为成功。组件加载失败已有原位说明，菜单与确认已有局部反馈，键盘异常进入notices。

`createNotices`仅保存文本、级别、来源、时间，最多50条；没有操作关联、解决状态或恢复引用，其读取也不是新提案的受限只读投影。监听器直接调用，订阅者异常可能让通知调用抛出；组件故障的内部`report`已有保护，但普通`ctx.notify`路径不能据此当成安全隔离完成。

平台记录安装失败与报告失败，但`list/start`快照可能包含原`Error`；这是内部诊断对象，不能原样跨IPC或交给通用呈现。组合根要求当前固定启动集合全部成功，失败会回滚并抛聚合错误；不把单组件挂载隔离扩大解释为所有启动失败都可继续。

## 3. 目标合同、流向与所有权

```text
UI组件故障 ──────────────→ UI宿主捕获、来源绑定 ───────┐
内核命令结果 → 应用服务 → 类型化桌面结果 → 集中适配 ──┤
其他插件问题 → 所属平台、服务或内核边界 → 集中适配 ───┤
                                                    ↓
                                  一份反馈记录与受限只读投影
                                    ↓                 ↓
                                  原位说明         现有状态入口

用户选择恢复 → 重新验证目标、版本和权限 → 原获准执行链
             → 状态所有者确认结果 → 更新关联反馈

需要留存的诊断 → 已获准宿主诊断端口 → 宿主日志
```

反馈记录描述操作的报告状态，不取代业务状态；诊断日志用于追溯，不取代当前UI反馈。两者可通过受控报告引用关联，不要求反馈显示必须等日志写入成功。

| 问题所在边界 | 谁决定结果与处置 | 如何到达UI／是否需要内核 |
| --- | --- | --- |
| 字段草稿无效、组件渲染或按键回调失败 | UI组件及其宿主 | 原位反馈；必要时交宿主诊断。通常不进入Core |
| 插件声明必填无效、安装或权限拒绝 | 平台／可信宿主 | 平台生成可读问题；不能依赖尚未启动的插件自行报告 |
| 乐谱命令、领域校验或扩展效果被拒绝 | 内核与原业务服务 | 沿真实结果返回；应用服务适配，UI显示原因和合法动作 |
| 功能插件的非业务异步任务失败 | 任务所属宿主／服务 | 受限报告端口输出；不为记录故障额外提交谱面事务 |
| 业务插件回调在内核事务路径失败 | 原事务或插件执行边界 | 由该边界决定拒绝、回滚与诊断；UI不得自行宣布回滚 |
| 文件、IPC、持久化或服务可用性问题 | 桌面／应用服务 | 返回宿主结果；可能影响业务可用性，但不能冒称Core拒绝 |
| UI失效需要暂停订阅、取消任务或结束会话 | 原资源与会话所有者 | 若已有获准生命周期端口，调用该端口；错误报告本身不是取消或结束命令 |

工程定版必须表达下列语义，具体字段名、版本、枚举和限值仍待工程发布：

- **业务结局与反馈状态分别表达**：确认提交、无变化、确认拒绝、部分步骤完成、结果待核对；警告、unsupported、取消也保留原合同含义。关闭或已查看不改变业务结局。
- **相关但不同的身份**：宿主绑定插件／组件实例／会话来源，关联真实操作、尝试和报告；诊断编号不能替代业务请求身份。不得按文字、错误码或时间相近猜测相同操作。
- **公开表达与私有诊断分离**：有可读安全摘要，稳定码按来源合同保留；raw Error/stack/业务载荷不进入通用投影。未知码可显示基础说明，详细信息和诊断导出另按许可处理。
- **恢复有真实条件**：动作可空；非空时引用已有获准动作。`retryable: true`只是已有结果提示，不自动产生可执行命令；缺省、false和不可用各自按合同处理。
- **报告失败不改业务结果**：记录、订阅者或呈现失败后，保持原事务结局与执行次数；宿主基础回退独立于失败呈现，防止报告错误递归。
- **订阅故障不等于写入失败**：若提交已确认但投影未刷新，显示更新暂不可用并重读获准投影；不得重发已提交写入。原位和全局消费共享关联记录，避免重复打扰。

插件共同最小声明仍只有共同身份、名称、插件版本和兼容要求，不强加`onError`、反馈贡献或内核依赖。可选反馈、动作与详情为空合法；已声明的扩展条目内部必填、权限与版本无效则按其合同拒绝。所有插件最终的宿主故障出口由平台兜底，不由插件自报能力是否存在决定。

## 4. 验证与错误矩阵

| 输入／情形 | 必须保持的结果 | 反馈与恢复要求 |
| --- | --- | --- |
| 内核明确拒绝 | 依原事务结果判断未提交 | 原处说明；已获准的重新定位／重新准备入口按实际能力提供 |
| 提交成功后通知或日志失败 | 原成功结果和执行次数不变 | 单独记录报告设施问题；不得再次执行业务 |
| IPC外层成功，能力结果为Rejected/Failed | 仍按内层业务分支处理 | 不用Promise兑现判断成功 |
| IPC超时、断连或提交后读取失败 | 未获结局证明时保持待核对 | 通过已有读端口或正式结果查询核对；不得自动重试写入 |
| 文档版本发生变化 | 不能证明某个请求已经提交 | 仅凭版本变化不宣布成功；没有可靠查询时继续保持待核对 |
| 重复请求／再次尝试 | 服从原请求去重与版本合同 | 不假设所有动作幂等；新尝试与旧报告明确关联 |
| 旧`HostError.issue`缺省 | 仍是宿主失败 | 基础可读说明；不伪造Core来源、定位、可重试或已解决 |
| 未知插件错误码 | 公开反馈合同内可展示 | 现有诊断日志不接受该码时保留反馈；诊断保存状态单独表达，不改白名单或偷换为已知码 |
| 原Error、超限／无效报告 | 对外使用安全基础说明，内部按实际许可诊断 | 不展示对象字符串、null、堆栈或任意HTML；保留原业务结局 |
| 可选动作／详情不存在 | 合法无贡献 | 不生成空按钮、空菜单或假的重试 |
| 已声明扩展必填为空／来源伪造 | 按所选接口合同拒绝 | 平台与宿主生成基础问题，不借此添加所有插件共同必填 |
| 来源组件隐藏或已释放 | 重要未解决问题仍按保留策略可达 | 不强开侧栏；失效实例不能更新新会话或调用旧恢复动作 |
| 异步完成晚于新尝试／新会话 | 旧更新不能覆盖新状态 | 校验来源、会话与次序；不能因忽略旧UI回写而假定原业务被取消 |
| 用户关闭、已查看或清空历史 | 不代表业务修复 | 未解决重要问题不能依普通历史上限静默消失 |
| 监听器、日志或呈现提供者失败 | 其他订阅与业务处理按合同保持 | 单独隔离、去重和基础可见回退；不循环调用失败通道 |
| 启动必需插件失败 | 保持已声明的启动失败／回滚策略 | 由宿主提供可读启动结果；不承诺当前组合根会降级运行 |

## 5. Good／Base／Bad案例

**Good：内核拒绝修改。** 原获准编辑动作收到明确Rejected，服务保留稳定错误码，UI在动作发生处显示“这次修改未完成”及真实可用的重新定位入口，关联记录保留。用户选择恢复后重新检查文档版本和权限，不由反馈呈现直接调用内核。

**Base：UI组件加载失败。** 宿主保留已存在的组件原位失败说明，将安全摘要与来源交给反馈合同；必要诊断通过宿主保存，纯Core文档和历史不因“记录UI故障”发生变化。反馈提供者故障时，宿主基础可见路径仍可达。

**Bad：超时后立即重试。** 原编辑可能已提交但返回丢失，呈现显示“乐谱保持原状”并再发一次写入。正确处理是显示结局待核对，依据现有端口可证明的结果决定后续；不能只读到不同版本就判断原请求成功，也不能借Agent专用收据假定普通UI已经拥有跨重启查询。

**部分完成：文件写入后检查点失败。** 现有应用服务明确存在“文件已写入，但内核无法确认保存检查点”的结果。反馈需要保留这个事实，不能改成“文件未保存”或“全部成功”。可提供的再次保存动作仍由文件服务合同与当前状态决定。

工程交接必须包含以下可断言场景，当前尚未运行：

1. 原位UI故障、内核拒绝、平台拒绝和宿主失败分别保持真实来源；UI故障上报不产生Core事务。
2. Committed、NoOp、Rejected、能力Unavailable/Failed及可用路径中的warning/unsupported分别处理；无`issue`的旧失败仍可见。
3. 同步返回、同步抛出、Promise拒绝、外层IPC拒绝和内层业务拒绝不混淆，原执行次数为一次。
4. 提交成功后订阅／日志失败不改变提交结果；传输结局未知时不自动写入重试，可靠查询缺失时不假成功。
5. 相同局部编号的两个插件不覆盖报告；旧会话与旧尝试完成不能改新报告或调用旧动作。
6. 未知码和缺省可选动作仍可读；诊断白名单拒绝不删除公开反馈；公开投影不泄露原Error与业务载荷。
7. 重要未解决问题在50条以上、目标隐藏／释放及清空普通历史后按合同可达；已查看不等于已解决。
8. 菜单、按钮与快捷键同一次执行只产生一个主要报告；原位说明与记录关联而非重复播报。
9. 反馈提供者和监听器失败有独立基础回退；其他订阅保持，报告无递归，释放后无旧回写。
10. 使用已发布合同新增插件或下一固定会话替换呈现，不修改既有功能插件；基础声明合法且无反馈贡献的插件仍可登记。
11. 恢复时目标、版本和权限变化再次被检查；UI不自行宣布重试安全、取消成功或事务回滚。
12. 中性视觉稿验证固定谱页、无侧栏遮挡、无白边／可见滚动条／默认动画；按需详情可用键盘关闭并恢复焦点。

## 7. 实施交接顺序与错误用法

1. 本会话维护反馈视觉与跨层边界：完成影响清单、语义矩阵和验收要求；第六批视觉按这些状态制作中性承载。
2. UI工程与桌面／内核工程确认已有执行端口、请求去重／结局核对能力与错误投影。集中适配正式输出；必要的新合同由所属工程会话发布，不把提案键名传入当前SDK。
3. UI工程发布报告与只读消费合同，给默认实现和未来提供者同一边界；迁移旧notify／confirm／结果出口，保留兼容和回退。
4. 对应工程会话完成一条真实业务成功／拒绝／不确定结局的纵向验证，再扩大具体插件制作。本会话复核呈现、焦点和几何，保留各层独立完成状态。

错误用法：每个插件直接导入某个通知UI；所有故障广播raw Error给内核；每个按钮各写错误码映射；未提供恢复动作时临时拼出重试；因反馈插件失败再调用同一插件记录其失败。

正确用法：真实执行边界保留业务结果与来源，宿主集中生成受限反馈投影，可替换呈现读取合同；诊断经获准宿主端口留存，恢复经原动作重新验证；反馈设施失败有独立小范围回退。内核不导入UI插件或通知实现。
