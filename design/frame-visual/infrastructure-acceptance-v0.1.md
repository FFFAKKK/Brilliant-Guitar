# 基础设施验收与插件开发稳定性标准 v0.1

日期：2026-10-07。状态：评审草案，供现有收尾审计和后续测试插件使用。写出本标准不代表已经通过标准。本轮不变更公共 API、运行代码或安装发布范围。

2026-10-09补充：本标准的完整资格门槛与日常开发准入分别判定。当前支持能力、有限收尾退出条件及待开发/发布事项见[开发准入范围](development-readiness-v0.1.md)。G1/G6/G7缺少完整证据不自动阻塞所有既有API下的受控功能开发；遇到具体合同/所有权/数据完整性缺陷时，必须先修相应边界。

## 1. 验收对象与范围

核心目标：作者仅依靠版本明确的项目文档、公开 SDK/类型、公开资源和已说明的装配入口，能够开发、测试、配置和运行支持范围内的插件；宿主在正常、失败、重复操作及重启场景中保持约定行为。

本轮对象是备份 `design/frame-visual` 的正式平台、UI 宿主、命令/菜单/快捷键、布局/视口、配置存储、核心谱面只读会话及桌面装配。整个内核、吉他重构及其他会话的独立模块，不因本轮通过而自动获得资格。

当前约束：一个正式 PluginPlatform、一个 UI router、启动时固定插件集合；Windows 为首个桌面目标；不做热插拔。外部安装/市场、第三方执行沙箱、自由放置和未开放业务接口后置。后置能力必须在支持表中明确，不能用其缺失否定已限定的能力，也不能把它们宣传为可用。

每次验收先填写支持表：能力、公共合同/版本、真实消费入口、状态所有者、允许调用者、同步/异步行为、失败/取消语义、验收用例和负责人。内置应用专用端口与普通插件 SDK 能力分别列出。

## 2. 三种完成声明

| 声明 | 必须满足 | 可据此开展的工作 |
| --- | --- | --- |
| 基础开发范围完成 | 支持表冻结；该范围内下述 G1–G8 必需项全部通过，证据对应同一候选版本 | 开发使用这些公开能力的插件，继续受控集成 |
| 插件开发稳定可用 | 基础开发范围完成；文档开发试验、组合/替换、重复运行及实际运行环境验证通过 | 按已承诺范围进行常规插件开发；扩大范围仍需追加资格 |
| 产品发布候选合格 | 稳定可用；真实打谱闭环、作品保护、性能和安装/升级等发布门禁通过 | 对实际候选安装包给出发布结论 |

当前只读资格不包含音符编辑、保存、历史、播放或六线谱。支持写入的基础设施必须通过相应真实业务流程后才能获得写入范围的声明；不能在没有业务消费者时仅凭接口设计宣称完整编辑基础已经成熟。

## 3. “仅凭文档开发”的验收

### 作者允许和禁止依赖的内容

允许：当前版本作者合同、公开 SDK 与类型声明、明确公开的宿主端口/资源、插件自己的代码和资源、文档说明的测试/构建命令及装配配置。

正常接入允许新增插件文件和修改应用明确公开的固定启动集合/装配配置。不能把这一项扩大为修改平台实现、私有状态、其他插件或公共接口来迎合测试插件。

作者不应需要阅读宿主私有实现、询问原作者隐藏规则、导入未公开内部模块、访问别人的 DOM/状态，或者再建平台、router、视口或谱面数据权威。需要尚未开放的能力时，应记录缺口并由接口所有者先设计和实现。

文档至少必须提供：完整可运行最小包、身份与版本、贡献字段与类型、公开导入路径、支持位置、权限/依赖、设置读写边界、命令参数/结果、异步/取消、生命周期、失败处理、装配/构建/测试步骤及兼容范围。

当前新作者入口是 [4.0 公共挂载合同](plugin-mount-contract-v4.md)；[作者文档](plugin-authoring.md)内的旧 v1 内容只能在明确标注的历史/内置迁移范围使用。权威入口必须链接精确字段合同，草案和历史示例不能被当作当前通用 SDK。

### 最少三类实际开发试验

| 试验 | 作者交付 | 验收要点 |
| --- | --- | --- |
| A：侧栏组件与设置 | 独立面板，读取本插件设置，声明资源释放 | 正常装配、设置先恢复、隐藏/移动不重建、释放清理；不访问私有布局 |
| B：命令与入口映射 | 无界面命令包，或带菜单/快捷键的独立包 | 同一命令实现保留参数/结果；每次只执行一次；未授权、禁用及输入框场景遵守合同 |
| C：工作区只读视图 | 独立 view，使用作者自己的输入或文档已公开的只读端口，处理异步和重试 | 唯一 view 冲突、失败回滚、过期结果丢弃、同实例生命周期；宿主继续拥有滚动和缩放 |

这些试验只消费已开放的能力。谱面交互读端口在正式开放后另加专项，不能以实例私有 `_scoreInteraction` 代替公共接口通过验收。

每个试验先记录作者读取的资料，再开发并验证；保存额外澄清、私有依赖及宿主修改次数。目标是没有隐藏规则依赖、没有未公开导入、没有为插件新增宿主特判。单纯复制内置插件不能独立证明文档足够。

本会话已经了解宿主源码，因此本会话自测只能证明示例可执行。完整的文档开发试验需要未阅读宿主私有实现的作者，或明确隔离实现源码的试验环境；不得把知情作者自测记为独立作者通过。当前 inline 模式不派发子代理。

对于已声明可替换的公共端口，应再接入一个满足相同合同的提供者，验证消费者不需修改。这个试验不增加插件平台、登记层或通用路由器。

## 4. 基础设施必需门槛

| ID | 门槛 | 通过条件和关键证据 |
| --- | --- | --- |
| G1 | 文档和公共合同完整 | 当前版本入口唯一可识别；字段/类型/错误/限制与代码一致；三类作者试验覆盖本轮支持能力；无隐藏实现依赖 |
| G2 | 实际消费与组合成立 | 声明经过同一平台捕获并被真实入口消费；按钮/菜单/快捷键经过同一 router；新增支持范围内插件无需改既有消费者；独占位置/依赖冲突行为明确 |
| G3 | 权限与所有权明确 | 插件只能执行授权命令和读取获准投影；设置、布局、文档与视口各有明确权威；重复 ID、越权、未知版本被安全拒绝；权限声明不被宣传为进程沙箱 |
| G4 | 生命周期与失败闭合 | 安装失败回滚；隐藏/移动/恢复符合合同；dispose 幂等；晚到结果不回写；异常后可按约定重试；监听、DOM、订阅、动画轨道等实际资源恢复到预期基线 |
| G5 | 数据一致性和持久化可靠 | 同一原子文档身份/版本驱动标题、读数和谱面；绘制及几何同版；读取/保存失败不会假成功或破坏已接受数据；配置保存后的新进程恢复已验证；写入范围另验保存/历史/恢复 |
| G6 | 重复运行和容量有依据 | 重复操作无累积资源增长、重复执行或污染后续会话；对支持的规模定义设备/输入/时延/资源阈值并实测；阈值或证据缺失记 pending |
| G7 | 同版实际环境验收 | 源码、依赖、生成资产和二进制可对应；候选前后指纹一致；真实 WebView 关键流程通过；Ctrl+滚轮、系统缩放、IME等与本轮支持范围相关的行为单独验证 |
| G8 | 版本演进可维护 | API、配置及作品格式各有版本边界；批准的旧输入 fixture 保持兼容或有显式迁移；不支持的未来版本安全拒绝；变更说明、支持表及回退方式对应候选版本 |

配置并发必须作出可执行选择：保证并验证一个写者，或提供已验证的跨写者冲突保护。当前单适配实例队列和文件原子替换不能被当作跨进程读改写事务；不能仅写“单实例”却不检查是否可能有第二个写者。

当前同一主线程内的同步插件代码不能靠计时器获得硬中断保证。取消、预算与性能指标需说明是实际强制约束、协作取消还是观测；未声明的强隔离能力不算完成。

G6 的候选回归方案：对启动/结束、隐藏/恢复、命令调用及异步结果替换分别执行100次可复现循环，记录每轮资源计数和最终状态。该次数是 v0.1 候选测试计划，不是已经跑过的结果，也不能证明所有长期负载。JS 堆受回收时机影响，应检查受控资源和多轮趋势，不能要求截图中的瞬时内存绝对不变。

性能验收表必须先写明目标设备、文档规模、操作、采样方式和阈值，再执行。不得在看到结果后修改阈值让它通过；目前没有批准的项目数值时，不自行把任意响应时间标作商业标准。

## 5. 怎么审计

1. 固定范围和候选版本。列出支持能力、目标环境、依赖与源/资产/EXE指纹，保留现状和测试数据；与其他会话的增量分开，不修改他人验收清单。
2. 对每个公开能力建立“文档 → 声明/类型 → 捕获/权限 → 真实消费者 → 回归 → 实际环境证据”的映射。没有消费者、无测试或只有历史结果的能力分别记录。
3. 优先复现一条窄的真实链：启动配置 → 注册/设置恢复 → 组件/命令 → 受控业务端口 → 文档投影 → 实际显示。先证明运行的是候选版本。
4. 按第3节做文档开发试验，记录作者阻塞点。错误入口、过时“当前”表述、缺少步骤、未公开依赖分别归档，不靠口头解释结束问题。
5. 对实际消费链注入可控失败：非法声明/权限、依赖缺失、设置读取/写入失败、挂载异常、延迟/逆序结果、释放后的结果、重试及重新启动。只模拟目标边界，不覆盖用户真实文件或配置。
6. 执行重复运行/容量检查，再验实际桌面候选包。DOM替身、Chrome DPR模拟、静态生成资产和真实Windows/WebView结果分别记录。
7. 每项 G 门槛逐项判定，输出问题清单和进入下一阶段的条件。旧证据只能复用到明确未受改动影响的范围；受影响部分重新验证。

可复用的检查入口：

```text
npm --prefix apps/workbench test
node apps/workbench/node_modules/typescript/bin/tsc --noEmit -p apps/workbench/tsconfig.json
npm --prefix design/frame-visual test
npm --prefix design/frame-visual run startup:check
npm --prefix design/frame-visual run motion:check
npm --prefix design/frame-visual run desktop:check
npm --prefix design/frame-visual run foundation:check
```

这些命令是已有检查入口，不是本轮已执行列表。桌面原生构建和窗口重放按 [桌面入口](desktop-entry-v0.1.md)及实际候选证据执行。每个修复先运行相关回归，集成边界改变后才扩大到相关全量；无需因文档排版修改重复整个运行测试矩阵。

2026-10-08续做的[持续边界回归](foundation-boundary-regression.md)提供统一定向入口，复用原正式/备份测试和生成器，拒绝空跑/跳过/超时以及验收中指纹漂移。它始终保留G1独立作者、G6容量及G7原生资格pending，不替代相应证据和全量测试。

## 6. 发现问题后怎样修复

每条问题记录：问题ID、支持范围、候选指纹、实际/预期行为、最小步骤及输入、最早失效边界、原因证据、影响、负责模块、修复和回归入口、最后状态。

严重度：P0为作品损坏/丢失、越权或不可恢复的状态破坏；P1为已支持主要流程失效、过期状态覆盖、重复执行，以及阻塞正常插件开发的合同缺口；P2为不改变合同或数据的非关键体验问题。证据缺失标为 pending，不能直接称为已经发生故障，也不能计为通过。

修复闭环：

1. 保存失败证据，在干净或可重置的测试基线上稳定复现。
2. 沿真实输入、捕获/验证、命令、状态、投影、渲染和资源释放追踪，找到最早与合同不符的位置。每次只改变一个验证变量。
3. 判断是实现违约、合同缺口、文档过时还是装配/生成版本不一致，修复责任归对应所有者。
4. 先增加能在修复前失败的语义回归，再修改造成问题的最小权威实现；检查其他消费者是否受同一原因影响。
5. 重新生成受影响资产，验证失败用例、相邻正常/取消/释放用例及所需集成检查，再在受影响的实际环境重放。
6. 更新原有权威合同、作者文档和候选证据，保留初次失败记录；记录剩余边界。接口变化应有版本或兼容策略，不让作者依靠历史口头说明。

Wrong：谱面位置错就加全局CSS偏移；旧结果覆盖就新增另一份音符状态；测试失败就改数量或放宽阈值。

Correct：先证明坐标、版本或状态在哪个边界失去一致性，修复该权威所有者；回归断言同一文档/版本及实际几何，恢复原资源基线。合法合同变化可以更新断言，但必须有变更依据和实际行为证据。

不能把所有异常写为“操作没发生”。已经提交但响应失败的写操作必须通过权威状态核对，或明确标记结局待核对；不得盲目重试非幂等写入，也不能假定取消Promise会撤销磁盘提交。

## 7. 判定、证据与失效规则

每项结论只有：passed（当前候选通过）、failed（复现不符）、pending（未验证/缺依据）、excluded（范围冻结时明确后置）、stale（相关实现已改变）。excluded不能在测试失败后临时补作豁免。

必需项只有 passed 才能计入完成；pending、failed、stale都阻止相应范围的稳定声明。修复严重度用于排序，不用于绕过发布必需门禁。普通已知问题是否允许留存，按既有发布范围和质量要求处理。

证据至少包含：支持表/合同版本、源码/依赖/资产/二进制指纹、环境、可重放步骤与输入、命令退出结果、实际观察和限制。测试总数不能替代断言范围，旧EXE、fixture和测试替身不能冒充新桌面真实作品。

当并发增量改变相关指纹，应结束当前候选判定，另建候选或等待该增量交付后重新生成/补验。已封存阶段保留；后续增量不能拿此前结果自动获得资格，也不应无限覆盖历史记录。

## 8. 当前应用方式和下一步

现有证据证明部分平台、命令、布局和桌面只读能力可用。2026-10-08最终同版已通过启动冲突/失败退出、配置保存重启及只读关键窗口流程；已有三组100次受控资源循环。
本标准的独立文档作者试验、设备/规模/阈值和长期资源容量、原生Ctrl+滚轮/系统缩放/IME仍pending，不宣称基础设施已商业成熟。最新范围及证据见[基础审计](research/infrastructure-foundation-audit-20261007.md)和[同版桌面验收](evidence/desktop-foundation-window-20261008/verification.md)。

首先收口文档版本入口及已开放能力表，完成当前布局增量交付并选定候选；随后执行三类作者试验、失败/生命周期和同版桌面验证。通过当前基础范围后，正式开放谱面同版交互读端口，并用复用的成熟输入模块形成编辑/撤销/保存/重开闭环。

小规模真实业务集成用于检验接口是否合适，不需要先等待全部未来插件能力；商业发布结论仍需针对实际产品闭环与安装包给出。
